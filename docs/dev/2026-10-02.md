## GitHub CI 的跨平台失败

问题：主干本机 `verify:full` 通过后，GitHub Actions 的 Linux `CI / verify` 连续失败并给制作人发送邮件。公开运行 #151 显示秘书重试测试假定香港时区，恢复集成测试的临时仓库只忽略目录形式 `node_modules/`，在 Linux 把指向目录的软链接当作未跟踪文件，导致指纹读取 `EISDIR` 和一个恢复预检失败。

范围：仅修测试时间构造与临时仓库忽略规则，让同一语义在 Windows 和 Linux 成立；不关闭 CI、不放宽游戏验收、不修改正式工作区的游戏草稿。验收：本机用 UTC 定向复核时区用例，完整门禁通过，随后以 GitHub 新运行的实际结论确认跨平台修复。

GitHub 新运行 #152 的原五项测试断言已关闭，但 `完整验证` 仍因测试环境启动失败：CI 按 `.nvmrc` 使用 Node 20，锁定的 `jsdom 30.0.1` 要求 Node `^22.22.2 || ^24.15.0 || >=26`，其依赖 `undici 8.10.2` 要求 Node `>=22.19.0`。本机 Node 24.18.0 的完整门禁已通过，因此将 `.nvmrc` 更新为 Node 24，并将这个独立 CI 控制文件纳入正式任务恢复时允许的控制面路径；新 GitHub 运行仍是最终跨平台证据。

## 工作流验收去重与职责边界

制作人再次明确：主 Agent 不代做游戏开发或实玩；其职责是修复正式 Agent 的环境、权限和恢复路由。正式开发的执行 Agent 自己完成当前树玩家路径操作并留下可核查证据；策划验收只核对批准方案兑现，QA 重点查 Bug 与回归，两个独立角色都实际操作但不互相重做整套场景。遇到无法实玩的环境阻断，保留失败及恢复点，由主 Agent 修控制面；仍无法解除就报告制作人，不跳过验收。

本轮控制面修订为停滞审查提供原运行一次性定向恢复：记录原 finding、制作人指导、选中的验证任务及下游，保留输入/输出仍有效的已完成任务，原执行会话补缺失证据；新轮同一阻断再次出现即停，不自动循环。节点规划拒绝把完全相同的验收检查分给两个任务。Feature 最终树的 `verify:full` 已覆盖 `verify`，因此不再在同一树单独先跑快速门禁；完整门禁自身改为静态检查加一次带覆盖率的单测，不再先跑普通单测后重复跑覆盖率单测。Task 范围无完整门禁时仍使用快速门禁。正式分支的游戏草稿保持原归属，控制面交付后仅在安全节点同步并由原工作流恢复。

控制面同步到正式分支后，首次定向恢复暴露预检错误：原阶段名为“增量复审”，旧条件只匹配“审查”，并且预检异常处理覆盖了尚未装载的 TaskRuns 索引。修复后预检失败保留原恢复点，复审阶段按实际审查历史识别。对于这一次已损失的索引，只有原审查连续三轮同缺口、原执行输出/日志及公开通过事件逐项存在、四份草稿哈希不变、其间合入路径均为已审计控制面时，才由正式恢复命令生成 `task-run-reconstruction.json`，恢复原任务索引；实现任务不重做，验证与交付定向重开。任何审计不符继续阻断，不用主 Agent 手工改运行状态。

正式续跑成功跳过前两项 Task，原验证 Agent 未重复执行 94 项已有断言，但其标准 Vite 启动在执行沙盒遭 `esbuild spawn EPERM`；浏览器自动审批拒绝 `http://127.0.0.1:5180/`，并明确禁止换入口绕过。Agent 如实把当前任务 JSON 改为 `blocked`，没有伪称实际页面操作。调度器却只据 Codex 进程退出码将验证 Task 记为 passed 并启动下游交付。主 Agent 在任务完成后中止该下游调用，保留进程最后已写恢复点；控制面追加正式任务 JSON 的阻断检查：执行者明确 blocked 时，停止下游 Task、门禁与复审，标记本项待环境恢复；异常恢复时同样不自动重跑。页面访问须由制作人解除权限阻断后，再由原工作流 Agent 续接。

## 问题、范围与验收

制作人要求在恢复正式工作流前更新新模型策略。此前常规及高级任务和审查仍使用 `gpt-6-sol`。本次只把这些活动路由更新为 `gpt-6.1-sol`，保留原有推理等级、Luna 轻量路由、Astra 关键决策路由及故障备用模型；不改变已批准的游戏范围、任务验收或权限边界。验收是策略校验、路由测试和最终控制面树门禁通过。
