# 秘书继续指令与真实调度

## 问题

制作人在钉钉要求“继续推进任务”后，秘书回复“收到”，但没有 Agent 启动。状态显示目标 Feature 仍为 `retry-wait`，并保留次日恢复时间。该行为不是使用错误，而是对话与调度状态机之间缺少真实迁移。

两个缺陷叠加造成了反复阻塞：

- `continue` 分支只写回复和通知，没有修改任务、恢复时间或触发调度。
- 从旧额度日志解析出的时钟时间已经过去时，系统直接顺延一天，造成不必要的长时间休眠。

## 修复

- 自然语言继续请求关联当前运行任务或第一项已批准排期。
- `retry-wait` 任务把恢复时刻原子改为当前请求时间，记录请求 ID，并在回复前唤醒协调器。
- 回复区分 Feature PM 已启动、任务本来就在运行、仍需具体产品决定和没有可执行排期，禁止无状态变化的空承诺。
- 只有时钟、没有日期的额度提示若已经过期，改为按短退避重新探测，而不是假定次日同一时间。
- 旧恢复点尚未产生任何任务结果、工作区干净且旧基线是当前提交祖先时，Feature PM 自动把空恢复点更新到当前基线；基础设施正常前进不再迫使制作人手动强制接管。

## 验收

- 单元测试覆盖继续请求解除未来恢复时间，以及过期额度提示的短退避。
- 单元测试覆盖无任务结果的旧恢复点安全更新基线。
- 真实秘书状态从 `retry-wait` 进入 `active`，并可观察到 Feature PM 进程。
- `npm run verify:full` 通过，包含 128 项 Vitest、覆盖率、资源沙盒、19 项 Playwright E2E 和生产构建。
