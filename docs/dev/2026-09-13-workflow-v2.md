# 稳定迭代工作流升级

## 背景

现有仓库已经具备测试、Git hooks、CI、ADR 和开发日志，但部分规则只存在于文字中，且主分支、版本、CI、发布触发条件和当前产品描述存在冲突。

## 实现

- 将 `master`、版本 tag 和 CI 触发条件对齐，tag 现在可以进入 Windows 打包任务。
- 统一 `verify:full`、`verify:ci` 与 CI 的验证链路：快速门禁、覆盖率、沙盒、E2E 和生产构建。
- 新增 `pre-push` 完整门禁、Node 版本文件、失败时的 Playwright 诊断产物。
- 新增文档与版本一致性检查，并纳入 `npm run verify`。
- 建立 `AGENTS.md`、`CONTRIBUTING.md`、当前状态、产品、架构、测试和功能规格文档层级。
- 增加 PR、功能提案与缺陷模板，并配置每周依赖更新。
- 发布脚本增加主分支、干净工作区与完整验证检查；无历史 tag 时从当前版本首次写入 CHANGELOG 的提交计算增量。

完整门禁首次运行时发现蓝图编译结果会在共享源码写回后被立即清空，且列表声明在 AST→蓝图转换中退化为数值类型。已让同名法术写回保留编译状态，并使蓝图声明节点完整保存列表元素类型与容量；对应 E2E 改为验证真实编译结果持续可见。

随后的真实界面验收又发现，作为语句的元法术调用在 AST→蓝图还原时没有重建参数连线，而嵌套语句编译会静默丢弃错误节点，导致「编译通过」但回写 DSL 丢失「发射」。已补全调用参数连线、向上传播嵌套编译错误，并将「列表类型与末层调用均必须往返保真」加入 E2E。

## 一次性迁移

- 当前历史没有版本 tag。根据 0.2.0 CHANGELOG 对应的阶段四内容，将 `e4e71fe` 记录为发布基线；下一个正式 tag 建立后脚本自动使用 tag。
- 仓库托管设置仍需人工开启 `master` 分支保护，并把 CI `verify` 设为必需检查。

## 验证

- `npm run docs:check`
- `npm run verify:full`
- `npm run release -- patch --dry`
