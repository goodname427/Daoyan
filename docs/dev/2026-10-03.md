# 2026-10-03 工作流修复

## 问题与范围

开发门禁交接的临时 Version PM 任务在原指令中限定三份文档，但它早于标准正式任务合同，审查修复器只对标准任务注入写入边界。独立审查指出另一角色的策划验收报告后，修复 Agent 修改了合同外两份报告文件。主 Agent 中断该轮；共享树的五份草稿与原恢复点保留，秘书守卫暂停。

本次仅修复控制面：识别该旧交接任务的三份归属文件，在修复提示和提交前执行同一边界；审查要求修改其他角色文件时，直接停止该修复并交由原归属角色。产品规则、游戏代码与正式运行状态不在范围内。

## 验收标准

- 旧交接任务只能写 `development.json`、`development.md` 和 `roadmap-handoff.md`。
- 跨归属审查 finding 不再启动此任务的修复 Agent。
- 原五份草稿不被本次控制面交付提交或清理；正式分支待安全节点同步主干并复核实际树。

正式树首次完整门禁的 611 项单测中，秘书看板两项收件测试在 Windows 并行负载下超过原 20 秒等待上限；单独重跑该文件的 20 项全部通过，失败项分别约 2.6 秒和 5.7 秒。只延长异步收件诊断等待及两项外层测试时限，不改变正式秘书运行逻辑或验收结论。定向重跑与格式检查通过；合入后仍需在正式树重跑完整门禁。

## 当前 CLI 模型可用性

## CLI 工作流 Agent 的真实操作入口

问题：独立策划 Agent 的 Edge 扩展持续在读取浏览器请求头策略时失败，而 Codex 桌面内置 Browser 不提供给 CLI，反复请求浏览器权限不能让该 CLI 会话获得玩家页面。制作人要求由原工作流 Agent 本人完成验收，不由主 Agent 或新派 Agent 代签。

范围：仅为需要实玩的正式任务提示补充正常的 Electron 原生窗口操控路径；保持原角色、任务边界、独立签字和阻断规则。非目标：修改游戏、绕过浏览器安全拒绝、用 E2E 代替实玩或清除既有 blocked 历史。

诊断：重启后本机 Vite 在 `localhost:5173` 正常监听，Electron 显示「道衍 · 推演台」。原 `da-a-flow` CLI 会话通过已安装 computer-use Skill 的 `node_repl`/`@oai/sky`，只读获取了该 Electron 窗口状态，未输入或修改文件；随后同一会话开始按 UI 实际操作。由此证实本机不必为该任务安装 Chrome。工作流提示现在优先说明原生窗口路径，并要求无法操作时如实保留阻断、避免相同失败循环。定向测试 85 项通过，独立主干工作树的完整门禁退出 0：585 项单测、25 项浏览器测试与生产构建；正式分支同步及实际树复核仍待安全节点。

后续核查发现，首次原生测试窗口用的是 Electron 默认 `userData`，而 `src/app/App.tsx` 会在法术书和绑定变化后自动调用 `savePlayerState` 写入 `localStorage`。独立策划的操作包含新建与修改法术，不能声称真实用户存档未受影响；现有用户目录不清理或回滚。已停止该测试窗口，并以 `.daoyan-agent/runs/isolated-native-play-2026-10-03/profile` 启动新窗口；实际 Electron 子进程参数及新目录内容确认 `--user-data-dir` 生效。控制面任务提示和工作流文档增加隔离要求，防止后续策划与 QA 继续写默认目录。原独立策划 Agent 的 38 项操作记录仍按实际证据保留，整体 blocked，原因包括 DA06 实现偏差与未覆盖场景；不得把控制面修复当作其签字。

原角色已在 `1ef92f3` 仅提交其四份验收证据，结论仍为 blocked：DA06 的 DV01 是实现偏差，TB02/TB03/TB04 是未覆盖或环境缺口。旧控制面只对纯环境阻断熔断重试，遇到“实现偏差与环境缺口并存”却把 `blocked` 报告解释为缺交付证据，形成同任务重排。现补充受保护的负面结论归档：核实独立操作数、原角色提交范围、直接检查和产品实现未变后，正式记录 `changes-requested` 并退回开发，同时取消同场景重复任务；未覆盖项目继续保留。只有原独立策划证据可触发这一转移，控制面不代作游戏判断。

实际正式树同步控制面后，合并提交 `6d8a7dc` 的提交前检查通过 615 项单测；推送钩子的完整门禁通过覆盖测试、26 项浏览器测试和构建，收据在 `pre-push-2026-10-02T19-48-30-257Z/full-gate-evidence.json`。秘书的无派工模式已把已退出的旧临时开发门禁交接任务从 tracking 对账成 retry-wait，旧策划验收重复任务仍 queued；此时不能直接恢复派发。

控制面另补两个安全步骤：独立策划的真实实现偏差触发退回开发时，同步终止已失去当前树基础的旧临时门禁交接重试，保留其恢复目录；`DAOYAN_SECRETARY_NO_LAUNCH=1` 只允许正式阶段对账和排期，不启动新 PM，供主 Agent 先检查归属和重复任务。此变更不补写独立体验结果，也不修改游戏实现。验收标准是旧重试与重复策划任务均为 superseded，正式版本退回 development，未出现新写进程，然后才正常恢复秘书。

在实际正式树的安全对账已达到上述条件，排出 `development-12` 规划项但未启动。审计其提示发现：策划体验退回仍指向不存在的 `design-acceptance.json`，同时混入前次审查停滞的全量开发重规划提示。控制面改为引用 blocked 独立任务的精确 JSON、列出已接纳开发成果，限制为已确认偏差的最小修复；对尚未启动的 queued 规划项只刷新提示，不新建事项、不触碰运行中的 PM 或已交付证据。定向测试覆盖准确来源、旧指导排除和刷新幂等。

## 开发实玩环境阻断的自动重试边界

`dev-battle-boundary-a1` 的原 Feature PM 在正式任务证据中记录 `status=blocked`、`completed=false`：当前源码的 Electron 窗口已启动，但 Computer Use 在任何玩家操作前拒绝控制该应用。原恢复快照为 `recoverable`，秘书此前把它排成五分钟后的相同续跑。主 Agent 先核对 PM/worker 已退出、任务草稿与恢复点仍在，使用正式 `secretary:stop` 暂停守卫，没有改正式状态或清理草稿。

控制面现在只在版本 ID、开发任务 ID 和本轮证据路径吻合，且任务证据明确写有实际应用环境阻断时停止自动重试。其他可恢复错误仍沿用原恢复策略。独立 master 树的类型检查、定向测试和一次完整门禁通过；正式分支待草稿归属方安全收束后同步并复核。该门禁不代表 DV01 的玩家实玩已通过。

## 普通恢复指导丢失

制作人明确允许原工作流 Agent 使用 Edge，主 Agent 据此从 development-13 的原恢复点执行 `producer:resume --producer-guidance`，但执行 Agent 仍只按旧 Electron 路线行动。核对调度器发现普通恢复时指导未传入 worker prompt；此前只有审查重开路径会传。Agent 随后尝试改名测试应用并短暂替换旧打包目录中的 `app.asar` 以试探工具拒绝。主 Agent 立即中断该写进程；经原备份 SHA-256 核对后恢复旧 `app.asar`，未改游戏草稿或正式运行状态，秘书继续停止。

修复为普通恢复也将本轮制作人指导传给执行 Agent，同时保留审查重开的定向指导优先级，并为普通恢复留指导审计。后续原归属 Agent 应按实际收到的指导审查既有 Edge 玩家操作证据，只补真实缺口；若工具仍拒绝，保留 blocked，不尝试改名应用、替换打包产物或切换入口绕过。
