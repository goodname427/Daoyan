# 稳定迭代工作流

本流程的目标不是增加手续，而是让每次迭代都具备明确范围、可验证结果、可回滚历史和可恢复上下文。

```text
制作人方向 → 版本策划与立项评审 → 详细策划与设计评审
          → 开发 → 策划体验验收 → 版本测试 → 缺陷修复 → 候选体验 → 版本归档
```

制作人不负责判断复杂度、拆分任务或选择模型。事件驱动的常驻秘书是唯一的跨版本入口；正式版本由主策、策划、Version PM、Feature PM 和测试 Agent 分阶段交付，主 Agent 仍负最终责任。版本立项和候选体验属于制作人固定门禁；其余只在产品方向冲突、不可逆选择、大版本发布，或必须由制作人恢复的账号、额度与外部访问阻塞时暂停。

常驻秘书的 notice guard 没有固定轮询，也不在空闲时调用模型。它只被制作人消息、结构化任务进度、PM 子进程退出、恢复定时器和外部通知唤醒；项目队列、已汇报节点和恢复状态写入 `.daoyan-agent/secretary/`。完整边界见 [ADR-0012](./adr/0012-事件驱动常驻秘书与交付PM分层.md)。

## 1. 需求进入

先把反馈转成可观察的问题，不直接把某个实现方案当成需求。记录：

- 玩家或开发者遇到的问题。
- 本次目标与明确非目标。
- 从起点到结果的完整用户流程。
- 成功、失败、空状态和往返状态的验收标准。
- 制作人所举例子背后的共通原则、原则能处理的相邻情形，以及策划补全时仍需确认的假设。

跨模块、需要多轮反馈或超过一个工作日的功能，从 [`specs/template.md`](./specs/template.md) 建立规格；显而易见的小修复可直接进入开发日志。

## 2. Definition of Ready

开始实现前应满足：

- [ ] 问题与玩家价值明确。
- [ ] 大范围产品方向已由策划提炼出系统原则、推荐体验和适用边界，并在立项评审中与制作人对齐；例子没有被当作封闭清单。
- [ ] 范围和非目标明确。
- [ ] 验收标准可以被测试或实际操作观察。
- [ ] 状态所有权和受影响模块已识别。
- [ ] 已判断是否需要 ADR、迁移或兼容方案。

条件不足时先澄清，不以大量代码探索代替需求判断。

实现细节、测试方式和模型选择不足不属于制作人澄清项，应由常驻秘书和 Feature PM 根据仓库事实决定。

## 3. 设计判断

- 难以撤销、改变核心语义或模块边界：先写 ADR。
- 跨模块但可回退：写功能规格中的技术方案。
- 局部实现选择：代码、测试或开发日志足够，不滥用 ADR。

任何方案都必须遵守 [`architecture/invariants.md`](./architecture/invariants.md)。

## 4. 分支与实现

- 主分支是 `master`，应始终可验证、可构建。
- 一个需求使用一个短期分支或独立工作树；避免多个不相关功能长期堆在主分支工作区。
- 分支建议：`feat/<name>`、`fix/<name>`、`docs/<name>`；Codex 使用 `codex/<name>`。
- 优先完成可体验的纵向切片，避免先铺大量无法运行的底层结构。
- 不回退或覆盖他人及工作区中与当前任务无关的修改。

新正式版本由一个逻辑 Version PM 贯穿：进入每个可执行节点时只拆该节点的可验收成果，按依赖逐项交给 Feature PM。Feature PM 自行拆内部执行步骤，在独占写入范围内完成一项成果、定向检查、独立审查和本地提交；执行 Agent 只做直接检查。Version PM 汇总各任务来源和实际命令，开发集成树最终运行一次 `verify:full`。Version QA 复用与验证树、修订、命令和配置一致的完整门禁证据，再补跨 Feature 验收。QA、候选和缺陷复验任务只写当前版本的证据目录。前置策划、代码、测试或验证配置变化会使完整门禁失效；后置 QA 和候选报告不会。旧正式版本维持原节点与证据合同。

每个节点在规划时给检查项指定唯一责任人、作用域和证据来源；同一节点的多个任务不得重复做相同验收，执行 Agent 不重复 Feature PM 的门禁，节点收束只汇总已通过的任务证据。后续节点先核对前序证据的代码树、配置、命令和场景是否仍匹配，再只做该节点新增的判断：策划验收核对设计兑现，QA 搜索缺陷和回归，候选核对最终构建及可体验性。审核者只审核本轮差异和证据，不重新执行测试或实玩。打回后只重开受影响任务与依赖，保留仍匹配的任务、命令和场景；同一缺口无进展即停止自动复审。有效证据可复用，不表示策划和 QA 两个独立角色可以互相代签。

节点任务结果的 `commands` 只记录交付时通过的直接检查，历史失败尝试及其真实退出码单列 `failedAttempts`，不能抹去失败或让已修复的旧尝试反复阻断接纳。同一节点交付因同一原因连续三次未被接纳时，秘书停止重派并交由主 Agent 核查证据与接纳合同。

普通类型、测试、格式或审查失败留在同一 Feature PM 运行内，按失败命令和未关闭 finding 迭代；新一轮发现新 finding 时继续原运行，不以固定轮数转交恢复。只有同一 finding 无进展重复、外部服务/额度阻塞、进程异常或持久证据损坏才进入恢复。pre-push 只消费代码树、完整门禁命令和配置指纹均匹配的成功证据，不再重复运行完整门禁。

新版本不再设独立的任务拆分和版本排期节点。Version PM 在当前节点写 `*-tasks.json`，声明任务 ID、目标、交付物、验收、直接依赖、读取路径和独占写入范围；秘书只按合同串行派发。范围冻结后的承诺变化仍按范围评审或下一版本候选处理。

版本策划、详细策划和主策审核节点的任务规划属于纯文档工作：只运行直接检查及任务清单的机器合同校验，不再额外调用通用独立审查模型。模块策划正文也走轻量档；主策在独立阶段检查策划语义、反例和跨模块自洽。开发节点规划仍保留独立审查，以检查实现任务的边界与风险。

版本策划只确定目标、范围、方向与受影响模块轮廓。详细策划节点由 Version PM 按实际模块拆出可独立审阅的成果，每个模块方案须写清状态和资源归属、规则、接口、跨模块交互、玩家流程、成功/失败/空状态、反例与验收情形；共用原则只维护一份权威正文。主策审核这些模块是否连成自洽的整体。若必须请制作人取舍，评审材料先以通俗语言解释各选项的玩家效果、优点、代价、推荐选择和理由；退回后回到详细策划修订，再复审。见 [ADR-0022](./adr/0022-模块详细策划与制作人取舍回退.md)。

开发集成完成后、独立版本 QA 前，增加主策或策划负责的策划体验验收。验收者先读已批准的模块方案，不参与该功能实现，以玩家身份运行游戏，逐项覆盖实际开发成果的主流程、边界流程和未被制作人举例的相邻情形。每个场景记录策划出处、操作步骤、预期、实际表现和可核查的运行证据，并绑定开发修订。结论不符即退回开发按偏差修正，修正后重新体验；策划语义仍有未批准的方向冲突则升级主策或制作人，不得修改策划文字让现有代码自动过关。该环节只检验游戏行为是否兑现策划，版本 QA 仍负责独立集成、回归与缺陷复验。纯文档版本可注明依据跳过。见 [ADR-0023](./adr/0023-策划黑盒体验验收.md)。

策划体验验收以已批准方案和玩家可见行为的一致性为主，QA 以寻找缺陷、回归和跨功能故障为主；两者都要由各自工作流 Agent 在对应的当前代码树上实际操作游戏。开发任务要求玩家闭环时，Feature PM 也要安排执行 Agent 完成该任务的真实页面操作与留证。自动化断言、主 Agent 的诊断操作、HTTP 可达或纸面预算都不能代替这些角色的实玩记录。若 Agent 无法打开或控制页面，主 Agent 只修复运行环境、权限和恢复路由；障碍未解除就保留技术阻断并报告制作人，不跳过实玩。已匹配当前树的命令、截图和场景证据按各节点职责复用，策划验收不重做 QA 缺陷搜索，QA 不重做策划逐条联签。

通过 Codex CLI 运行的工作流 Agent 可按宿主已安装的 computer-use Skill，使用 `node_repl` 与 `@oai/sky` 正常控制道衍 Electron 窗口；先唯一定位窗口，再逐步观察、操作和留证。可写实玩必须以本任务独立、保留的 `--user-data-dir` 启动 Electron，并从实际进程参数核实隔离目录；默认窗口会自动保存法术书到真实用户目录，不能用作可写测试窗口。桌面端内置 Browser 不会自动提供给 CLI；可用的浏览器扩展是另一正常入口。工具或安全策略明确拒绝时不得通过换端口、原始 CDP 等方式绕过。原生窗口仅被发现或显示、自动化 E2E 通过，都不能记成角色本人完成实玩。

computer-use 文档中的 `Screenshot.url` 为当前观察的 data URL。任务需要持久截图时，可将其字节写入该任务独占证据目录并核对文件和场景关联；不得仅为重复查看而解码、保存或再次抓图。若当前工具环境不能写出，保留截图缺口，不虚构证据。

独立策划若以真实玩家操作确认实现偏差，可保留任务结果 `blocked` 和未覆盖项。秘书只在该证据由原任务角色提交、直接检查成功、提交范围符合任务合同且受验产品实现未变时，采纳这一负面结论并回到开发；同场景的已排重试随之取消。开发修复后仅复验偏差及仍未覆盖的必验项，不把负面结论当作策划验收通过。

规划和纯文档阶段使用轻量 Profile，只执行直接相关的文档、类型或定向检查，不进入 Feature 快速门禁、独立代码审查或完整门禁，也不生成代码完整门禁证据；推送时显式沿用该轻量结论，不由 pre-push 补跑代码门禁。Version Profile 由测试 Agent 执行版本集成、回归、迁移、打包和候选命令，只复用匹配的 Feature 完整门禁并接受阶段报告复核，不重跑 Feature 快速/完整门禁。Task Profile 在没有完整门禁时使用快速门禁与独立审查；Feature Profile 先独立审查，再执行一次已包含快速检查的最终完整门禁，避免在同一代码树重复运行 `verify`。其余正式版本阶段仍按既有产品门禁收束。Task 层快速门禁使用：

```bash
npm run verify
```

快速门禁第一次执行聚合命令；若其中一个子命令失败，恢复点会记录此前已完成项和从失败点开始的待执行队列，修复后先重跑失败子命令，再依次执行原聚合链中尚未运行的后续检查。独立审查第一次读取版本基线差异；每次修复前保存代码边界，后续复审只读取未关闭 finding 及该边界后的文件增量。各阶段完成事实绑定候选验证树和配置指纹；恢复时复用仍匹配的快速门禁和审查，匹配的完整门禁事实存在时直接跳过上游审查。最终树变化后完整门禁证据自然失效，但已通过的快速子命令和上一轮整版审查不重放。

## 5. 自动验证

门禁定义见 [`testing.md`](./testing.md)。**下列完整门禁适用于实现交付的最终代码树**；规划和纯文档阶段按上文轻量 Profile 执行直接检查，不运行它：

```bash
npm run verify:full
```

`verify:full` 与 CI 使用同一条链路：快速门禁、覆盖率、沙盒、E2E 和生产构建。新版本由开发节点的 Version PM 在各 Feature PM 提交后的集成代码树运行；缺陷修复改变代码时由修复节点重新运行。Version QA 只消费仍匹配的证据，再记录跨任务测试结论。旧版本仍按原 Feature scope 合同执行。失败必须修复或明确说明阻塞，不能用“本地看起来正常”代替。

秘书排期统计先应用稳定事项关系和关闭事实，再去重原候选。任何被 `secretary:<id>` 后继引用的源事项，即使自身没有历史自引用，也与后继归一到同一关系根；活动事实优先覆盖 backlog，不能重复计数。取消、替代、合并或交付后必须反向闭合原候选；`merged` 与其他关闭事实同为终态。一次性兼容迁移只能绑定既有事项的稳定 ID/稳定键或迁移版本，禁止用主题文本正则持续匹配未来候选。兼容迁移产生的排期更正通过持久去重 ID 主动通知；每条发送成功后立即原子保存 `correctionSentAt`，再处理下一条，不能依赖整批成功、后续对账变化或仅在一次问答中临时修正文案。

## 6. 真实体验

Electron 间歇性退出诊断可显式设置 `DAOYAN_ELECTRON_DIAGNOSTICS_FILE` 为隔离证据目录内的绝对 JSONL 文件路径，再按正常入口启动应用。日志记录窗口关闭、主进程退出、渲染/子进程失败及加载失败；默认关闭，写入失败不会阻止启动，异常监视不吞异常。仍须使用独立 `--user-data-dir`，诊断不主动采集页面 URL 或存档，异常堆栈保留在本地；强制结束或断电可能没有最后退出记录，不能仅凭缺行认定崩溃。运行证据、profile 与日志放在 `.daoyan-agent/` 下，避免进入 Vite 源码监听；正式脏工作区先保持原归属，不能为了启用诊断强行合并主干。

涉及运行行为或界面变化时，自动测试通过后启动实际应用：

```bash
npm start
# 或
npm run desktop
```

按规格中的用户流程操作，并检查受影响的桌面与窄屏视口。UI 改动至少检查：可达性、滚动、溢出、空状态、错误状态、页签往返和控制台错误。

诊断本机启动失败时分别记录 Vite 服务退出、Electron 进程退出和操作工具拒绝，不根据窗口消失推断权限原因。隔离存档与运行证据放在 `.daoyan-agent/`；Vite 必须排除该目录的文件监听，避免 Windows 锁定的 Chromium 缓存使服务崩溃。记录诊断进程的退出时间和是否主动停止；服务 HTTP 200、窗口存活都不能代替玩家实玩。

## 7. 审查与合并

合并前：

1. 阅读完整 `git diff`，清除调试代码、重复实现和无关修改。
2. 检查测试是否覆盖行为而非只覆盖渲染成功。
3. 同步规格、长期文档、`status.md` 和开发日志。
4. 使用 Conventional Commits 形成可回滚的逻辑提交。
5. Pull Request 填写验收结果、验证命令、实际体验和风险。

本项目由 AI 负责日常版本管理。逻辑改动达到 Definition of Done 后应主动提交，并按协作状态决定推送；tag 只在版本号、发布说明和验证产物都匹配时创建，不等待用户逐次授权。大版本发布必须由用户明确决定。

主分支应启用保护，只允许完整 CI 通过后合并。

## 8. Definition of Done

下列清单适用于实现交付；规划和纯文档交付以内容评审、直接相关检查、范围与状态同步、可回滚提交为完成标准，不要求游戏 E2E、启动体验或完整代码门禁：

- [ ] 验收标准全部满足，包含错误、空状态和往返行为。
- [ ] 风险相称的单元、集成和 E2E 测试已经加入。
- [ ] `npm run verify:full` 通过。
- [ ] 实际应用已启动并按用户流程体验。
- [ ] 有可玩变化的正式版本已通过策划独立黑盒体验验收，结果与已批准方案及当前开发修订对应。
- [ ] 没有新增未解释的控制台错误、布局溢出或乱码。
- [ ] 长期文档、当前状态和开发日志已同步。
- [ ] 改动可通过一个或多个逻辑提交独立回滚。
- [ ] 用户获得可直接体验的地址、安装包或明确操作入口。

## 9. 发布

1. 确认工作区干净、处于 `master` 且完整验证通过。
2. 预览：`npm run release -- patch --dry`。
3. 发布脚本升级版本、生成 CHANGELOG、创建提交和 annotated tag。
4. AI 审查版本差异后推送分支和 tag；大版本发布在此之前取得用户明确决定。
5. tag 触发 CI 完整验证和 Windows 安装包构建。
6. 下载并冒烟测试产物，再对外宣布版本。

当前仓库历史没有版本 tag，`scripts/release-baseline.json` 暂时记录 0.2.0 的历史基线。下一个正式 tag 建立后，发布脚本自动以 tag 为准。

## 10. 反馈回流

用户反馈优先回写到原规格的验收标准；若是新问题则建立新规格或 issue。验收后的规格保留，开发日志只记录过程，稳定结论必须进入产品、架构或测试文档。

每个正式版本归档时，秘书在不调用模型的情况下生成 `.daoyan-agent/retrospectives/<version-id>.json` 和 `.md`。复盘统计各节点 Agent 调用、已知 token 下界、缺失用量、阶段运行、恢复、策划退回及 Feature 完整门禁证据；原始日志和阶段结论保持可追溯，未知值不能当作零。复盘与归档通知一起交付，报告生成故障由主 Agent 修复，但不阻断已获制作人批准的版本合回主干。

主 Agent 在下一版启动前从高成本或重复项挑一项做小规模对照：重复的取数、合同校验、格式化和汇总优先做确定性脚本；已经跨版本稳定、仍需人判断的操作顺序才做短 Skill。以接受任务的总调用、已知 token、缺失用量、耗时、退回与黑盒验收质量共同评价。复盘只提出调查与试验，不自动删减策划输入、降低模型能力或放松产品门禁。
