# 稳定迭代工作流

本流程的目标不是增加手续，而是让每次迭代都具备明确范围、可验证结果、可回滚历史和可恢复上下文。

```text
制作人方向 → 版本策划与评审 → 详细策划 → 任务拆分与范围冻结
          → Feature 开发 → 版本测试 → 缺陷修复 → 候选体验 → 版本归档
```

制作人不负责判断复杂度、拆分任务或选择模型。事件驱动的常驻秘书是唯一的跨版本入口；正式版本由主策、策划、Version PM、Feature PM 和测试 Agent 分阶段交付，主 Agent 仍负最终责任。版本立项和候选体验属于制作人固定门禁；其余只在产品方向冲突、不可逆选择、大版本发布，或必须由制作人恢复的账号、额度与外部访问阻塞时暂停。

常驻秘书的 notice guard 没有固定轮询，也不在空闲时调用模型。它只被制作人消息、结构化任务进度、PM 子进程退出、恢复定时器和外部通知唤醒；项目队列、已汇报节点和恢复状态写入 `.daoyan-agent/secretary/`。完整边界见 [ADR-0012](./adr/0012-事件驱动常驻秘书与交付PM分层.md)。

## 1. 需求进入

先把反馈转成可观察的问题，不直接把某个实现方案当成需求。记录：

- 玩家或开发者遇到的问题。
- 本次目标与明确非目标。
- 从起点到结果的完整用户流程。
- 成功、失败、空状态和往返状态的验收标准。
- 制作人所举例子背后的共通原则、原则能处理的相邻情形，以及策划补全时仍需确认的假设。

跨模块、需要多轮反馈或超过一个工作日的功能，从 [`specs/template.md`](./specs/template.md) 建立规格；显而易见的小修复可直接进入开发日志。

## 2. Definition of Ready

开始实现前应满足：

- [ ] 问题与玩家价值明确。
- [ ] 大范围产品方向已由策划提炼出系统原则、推荐体验和适用边界，并在立项评审中与制作人对齐；例子没有被当作封闭清单。
- [ ] 范围和非目标明确。
- [ ] 验收标准可以被测试或实际操作观察。
- [ ] 状态所有权和受影响模块已识别。
- [ ] 已判断是否需要 ADR、迁移或兼容方案。

条件不足时先澄清，不以大量代码探索代替需求判断。

实现细节、测试方式和模型选择不足不属于制作人澄清项，应由常驻秘书和 Feature PM 根据仓库事实决定。

## 3. 设计判断

- 难以撤销、改变核心语义或模块边界：先写 ADR。
- 跨模块但可回退：写功能规格中的技术方案。
- 局部实现选择：代码、测试或开发日志足够，不滥用 ADR。

任何方案都必须遵守 [`architecture/invariants.md`](./architecture/invariants.md)。

## 4. 分支与实现

- 主分支是 `master`，应始终可验证、可构建。
- 一个需求使用一个短期分支或独立工作树；避免多个不相关功能长期堆在主分支工作区。
- 分支建议：`feat/<name>`、`fix/<name>`、`docs/<name>`；Codex 使用 `codex/<name>`。
- 优先完成可体验的纵向切片，避免先铺大量无法运行的底层结构。
- 不回退或覆盖他人及工作区中与当前任务无关的修改。

执行 Agent 只运行与改动直接相关的类型检查、定向测试或文档校验，并逐条记录实际命令与退出码以及工作项范围、Git tree 和配置指纹；不得把任务拆分中的计划验收命令推定为已成功执行，也不得把 `verify`、`verify:full`、E2E 或 build 登记成 Task scope 证据。Feature PM 汇总有效 Task 证据后运行一次快速门禁、组织独立审查，并且是最终代码树上唯一执行 `npm run verify:full`、产出 Feature scope 完整门禁证据的责任者。修复仅复核问题、修复和受影响增量；恢复点除建议路径、实际输出和路径外只读直接依赖外，还保存当时相对 HEAD 的脏路径及内容哈希/删除标记。续跑只把这份基线之后新增、修改、删除或还原到 HEAD 的路径用于计划归属判断，再重算 Task 输入、输出和指纹并沿依赖只失效下游；接管前已经存在且内容未变的无关现场不参与判断，旧恢复点缺少该可选基线时继续按当前完整脏路径保守处理。Version QA 只有在实时计算的候选验证树、代码修订、完整门禁命令和配置指纹全部匹配，并确认 Feature 成功执行 `npm run verify:full` 时才能复用该事实；候选验证树覆盖代码、测试、验证配置以及章程、范围、规划、设计、`task-breakdown` 和门禁前生成的 `development.json`/`development.md`，只排除门禁后生成的 `qa`、`bugfix`、`bugfix-reverification`、`candidate`、`producer-acceptance`、`archived` Markdown/JSON 阶段报告。后置报告不会自行使证据失效，任何前置范围输入、开发逐项清单、代码或测试变化仍会失效。Version QA 随后负责跨 Feature 集成、主线回归、迁移、打包和候选验证，不重复运行 `verify:full` 或 Feature 局部自测。

普通类型、测试、格式或审查失败留在同一 Feature PM 运行内，按失败命令和未关闭 finding 迭代；新一轮发现新 finding 时继续原运行，不以固定轮数转交恢复。只有同一 finding 无进展重复、外部服务/额度阻塞、进程异常或持久证据损坏才进入恢复。pre-push 只消费代码树、完整门禁命令和配置指纹均匹配的成功证据，不再重复运行完整门禁。

任务拆分后的版本排期由 Version PM 形成 `version-planning.md`：按依赖标明波次、关键路径、允许并行度、容量上限和冻结范围。排期只能消费已核验的工作项，不得生成开发或 QA 通过证据，也不得手工推进版本节点；范围冻结后的承诺变化按范围评审或下一版本候选处理。

规划和纯文档阶段使用轻量 Profile，只执行直接相关的文档、类型或定向检查，不进入 Feature 快速门禁、独立代码审查或完整门禁，也不生成代码完整门禁证据；推送时显式沿用该轻量结论，不由 pre-push 补跑代码门禁。Version Profile 由测试 Agent 执行版本集成、回归、迁移、打包和候选命令，只复用匹配的 Feature 完整门禁并接受阶段报告复核，不重跑 Feature 快速/完整门禁。Task/Feature Profile 才进入 Feature PM 的快速门禁、独立审查和最终完整门禁。其余正式版本阶段仍按既有产品门禁收束。Feature 层快速门禁使用：

```bash
npm run verify
```

快速门禁第一次执行聚合命令；若其中一个子命令失败，恢复点会记录此前已完成项和从失败点开始的待执行队列，修复后先重跑失败子命令，再依次执行原聚合链中尚未运行的后续检查。独立审查第一次读取版本基线差异；每次修复前保存代码边界，后续复审只读取未关闭 finding 及该边界后的文件增量。各阶段完成事实绑定候选验证树和配置指纹；恢复时复用仍匹配的快速门禁和审查，匹配的完整门禁事实存在时直接跳过两者。最终树变化后完整门禁证据自然失效，但已通过的快速子命令和上一轮整版审查不重放。

## 5. 自动验证

门禁定义见 [`testing.md`](./testing.md)。交付前必须运行：

```bash
npm run verify:full
```

`verify:full` 与 CI 使用同一条链路：快速门禁、覆盖率、沙盒、E2E 和生产构建。它由 Feature PM 在最终代码树上执行一次，并作为 Feature scope 的完整门禁证据；Version QA 仅在代码树、命令及配置指纹仍匹配时消费该事实，再记录自己的 Version scope 集成、迁移、打包和候选结论。若候选代码使该证据失效，回到 Feature PM 重新生成，不由 Version QA 重复生成同一完整门禁。失败必须修复或明确说明阻塞，不能用“本地看起来正常”代替。

秘书排期统计先应用稳定事项关系和关闭事实，再去重原候选。任何被 `secretary:<id>` 后继引用的源事项，即使自身没有历史自引用，也与后继归一到同一关系根；活动事实优先覆盖 backlog，不能重复计数。取消、替代、合并或交付后必须反向闭合原候选；`merged` 与其他关闭事实同为终态。一次性兼容迁移只能绑定既有事项的稳定 ID/稳定键或迁移版本，禁止用主题文本正则持续匹配未来候选。兼容迁移产生的排期更正通过持久去重 ID 主动通知；每条发送成功后立即原子保存 `correctionSentAt`，再处理下一条，不能依赖整批成功、后续对账变化或仅在一次问答中临时修正文案。

## 6. 真实体验

自动测试通过后启动实际应用：

```bash
npm start
# 或
npm run desktop
```

按规格中的用户流程操作，并检查受影响的桌面与窄屏视口。UI 改动至少检查：可达性、滚动、溢出、空状态、错误状态、页签往返和控制台错误。

## 7. 审查与合并

合并前：

1. 阅读完整 `git diff`，清除调试代码、重复实现和无关修改。
2. 检查测试是否覆盖行为而非只覆盖渲染成功。
3. 同步规格、长期文档、`status.md` 和开发日志。
4. 使用 Conventional Commits 形成可回滚的逻辑提交。
5. Pull Request 填写验收结果、验证命令、实际体验和风险。

本项目由 AI 负责日常版本管理。逻辑改动达到 Definition of Done 后应主动提交，并按协作状态决定推送；tag 只在版本号、发布说明和验证产物都匹配时创建，不等待用户逐次授权。大版本发布必须由用户明确决定。

主分支应启用保护，只允许完整 CI 通过后合并。

## 8. Definition of Done

只有全部满足才能称为完成：

- [ ] 验收标准全部满足，包含错误、空状态和往返行为。
- [ ] 风险相称的单元、集成和 E2E 测试已经加入。
- [ ] `npm run verify:full` 通过。
- [ ] 实际应用已启动并按用户流程体验。
- [ ] 没有新增未解释的控制台错误、布局溢出或乱码。
- [ ] 长期文档、当前状态和开发日志已同步。
- [ ] 改动可通过一个或多个逻辑提交独立回滚。
- [ ] 用户获得可直接体验的地址、安装包或明确操作入口。

## 9. 发布

1. 确认工作区干净、处于 `master` 且完整验证通过。
2. 预览：`npm run release -- patch --dry`。
3. 发布脚本升级版本、生成 CHANGELOG、创建提交和 annotated tag。
4. AI 审查版本差异后推送分支和 tag；大版本发布在此之前取得用户明确决定。
5. tag 触发 CI 完整验证和 Windows 安装包构建。
6. 下载并冒烟测试产物，再对外宣布版本。

当前仓库历史没有版本 tag，`scripts/release-baseline.json` 暂时记录 0.2.0 的历史基线。下一个正式 tag 建立后，发布脚本自动以 tag 为准。

## 10. 反馈回流

用户反馈优先回写到原规格的验收标准；若是新问题则建立新规格或 issue。验收后的规格保留，开发日志只记录过程，稳定结论必须进入产品、架构或测试文档。
