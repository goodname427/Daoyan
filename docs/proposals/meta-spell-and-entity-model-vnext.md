# 元法术与统一实体模型 vNext

- 状态：关键决策已采纳，核心纵向切片已实现
- 提出日期：2026-09-13
- 触发问题：玩家不知道如何编写新法术；现有基础能力不足以组合出足够多的效果

本文保留最初讨论与备选方案，作为决策来源而非当前使用说明。已采纳结论以 [ADR 0009](../adr/0009-统一实体句柄与能力判定.md)、[ADR 0010](../adr/0010-动态元法术价格与静态上界.md)、[ADR 0011](../adr/0011-无界效果与动态资源预算.md) 和[动态预算纵向切片规格](../specs/2026-09-14-dynamic-meta-resource-budget.md)为准。

并发施法已由 [`../adr/0007-并发施法与共享资源账户.md`](../adr/0007-并发施法与共享资源账户.md) 单独采纳并实现。动态价格、统一句柄与能力判定已经采纳；神识强度、全面迁移旧元法术与移除冷却仍需按后续规格实施。

## 已采纳结论

- 强度参数统一表示“请求效果”；系统按效果、距离和关系确定性计价，不引入随机成功率。
- 有限效果请求不设人为最大值，运行时同时结算法力与 tick；分析器显示已知预算并显式标记未解析的动态项。
- Actor 与 Projectile 共用不复用的句柄，但按可选能力而非完整 Actor 属性判断操作。
- 查询以单属性为基础；创建返回句柄或 `空`，控制返回 `bool`，领域失败不产生部分修改。
- Projectile 当前只有有限寿命；未来可选 Vitality。每位所有者最多同时保有 16 个。
- 神识强度若引入，只影响确定性成本与可达阈值，不与神识上限混用。
- 固定减伤与冷却暂时保留，另行迁移。

## 目标

1. 玩家能从少量稳定的大类理解“我可以感知什么、计算什么、创造什么、控制什么”。
2. 元法术可以组合出更深的行为，而不是每种效果都依赖一个封装好的专用技能。
3. 强度、作用距离、目标抗性和施法者能力共同形成可解释的资源成本。
4. Actor、Projectile 和未来世界对象使用同一种实体句柄与能力判定。
5. 不依靠冷却强行限制自由度，主要由法力、施法时间、神识和世界条件形成约束。

## 拟议元法术大类

### 1. 运算符

用于数值、布尔、向量、列表和实体句柄的纯计算。只有时间消耗，没有法力消耗。

当前可迁入：`运算`、`向量`，以及不读取世界的 `长度`。后续可补齐钳制、插值、角度、点积、排序或筛选等基础计算，但必须继续满足静态可分析约束。

意见：这个合并是合理的。“向量”是数据类型，不必单独成为玩家心智中的世界交互类别。UI 内仍可用二级标签区分数值、逻辑、向量和列表。

### 2. 按键状态

用于读取虚拟按键的按住、按下边沿、松开边沿和蓄力时间。只有时间消耗，没有法力消耗。

当前可迁入：`按键按住`、`按键按下`、`按键松开`、`按键蓄力`。

意见：`结束施法` 不是按键状态读取，建议另归“施法控制”或作为语言级语句。否则分类名称会再次与真实职责不一致。

### 3. 状态探查

读取自己或其他实体的状态，包括位置、生命、法力、属性、阵营、标签和组件。拥有法力与时间消耗。

拟议影响因素：

- 施法者与目标的距离。
- 目标的神识强度或抗探查能力。
- 施法者自己的神识强度。
- 请求的信息深度，例如只确认存在、读取一个属性或获取完整快照。

意见：自身状态与远程探查最好保留不同的基础成本。读取自己已经拥有的状态不应被目标抗性影响；远程探查才进入对抗公式。

### 4. 实体控制

移动、旋转、造成伤害、改变属性、设置速度或控制已有实体。拥有法力与时间消耗。

拟议影响因素：

- 施法者与受控实体的距离。
- 受控实体的神识强度或控制抗性。
- 施法者自己的神识强度。
- 请求的强度、持续时间和变化量。

意见：应区分“控制自己的实体”“控制自己创建且仍拥有的实体”“强制控制敌对实体”。三者若使用同一价格，会让移动自身过贵或控制敌人过于廉价。

### 5. 实体创建

按系统允许的原型创建实体，例如 Projectile。创建时不直接修改原型属性，创建后再通过实体控制调整。

拟议影响因素：创建原型的基础价格、数量和生命周期。返回统一 `entity` 句柄，供后续控制。

意见：方向正确，它能把现在的 `发射` 拆成“创建 → 设置方向/速度/威力 → 发射或激活”，显著增加组合深度。但必须定义创建失败、实体所有权、最大存活数量、未激活实体和垃圾回收，否则玩家可以积累无限对象绕过资源约束。

## 数值、强度与法力输入

期望是：涉及强度的元法术由上层法术传入数值，输入越高，效果和消耗越高。

这里有三种不同语义，不能混用：

| 方案          | 调用者输入            | 系统计算           | 优点                 | 风险                           |
| ------------- | --------------------- | ------------------ | -------------------- | ------------------------------ |
| A. 请求效果   | 目标强度，例如伤害 30 | 达成该效果所需法力 | 代码直观，效果可预测 | 法力不足时需要定义失败或降级   |
| B. 投入法力   | 愿意投入的法力 30     | 最终效果           | 成本完全由玩家控制   | 很难直接表达“我要造成多少伤害” |
| C. 效果与预算 | 请求强度 + 最大投入   | 在预算内尽量达成   | 可表达策略和降级     | 参数多，静态分析与蓝图更复杂   |

建议优先选择 **A 或 B 作为全局一致规则**，不要让每个元法术各自决定。若采用 C，元法术应返回实际完成量或成功状态，不能静默截断。

一个待讨论的概念公式：

```text
基础负担 = 原型或操作的固定成本
距离负担 = 距离 × 距离系数
对抗倍率 = 目标神识强度 / max(施法者神识强度, 最小值)
强度负担 = 请求效果或投入法力对应的曲线

最终法力 = 基础负担 + 距离负担 × 对抗倍率 + 强度负担
最终 tick = 基础 tick + 距离/对抗/强度对应的时间负担
```

这只是讨论骨架，不是已确定公式。距离是否影响时间、神识强度是线性还是阈值、己方实体是否享有所有权折扣，都需要通过推演样例验证。

## 静态上界冲突

动态价格会直接影响 ADR 0001 的“创建法术时可预估成本”和架构不变量中的“静态上界可信”。目标距离和神识强度只有运行时才知道，分析器无法凭 AST 给出一个有限且精确的单值。

可选解法：

1. **显式预算**：元法术参数必须包含最大距离、最大投入或预算，静态分析按预算计价。
2. **场景上界**：推演台提供目标属性与距离范围，显示该场景下的上界，而不是法术的全局上界。
3. **公式而非单值**：法术面板显示 `基础 + 距离项 + 对抗项`，实战再显示实际值。
4. **组合方案**：编译时显示调用者可控预算上界，推演时带入目标数据给出场景实测。

建议采用组合方案。否则动态成本越丰富，静态面板越容易失去可信度。

## 拟议统一实体模型

Projectile 应成为统一 `entity` 可引用对象，但“统一实体”不等于“每个实体必须拥有全部 Actor 属性”。建议使用能力组件表达可选逻辑：

```text
Entity
├─ Identity：id、原型、标签、阵营、所有者
├─ Transform：位置、旋转、半径
├─ Vitality?：当前生命、生命上限、死亡规则
├─ Caster?：当前法力、法力上限、回复、神识、施法属性
├─ Movement?：速度、期望方向、移动规则
├─ Body?：肉体强度、碰撞、受力
├─ Projectile?：伤害、穿透、寿命、命中记录
└─ Modifiers?：临时属性变化
```

这样 Projectile 可以是实体并被移动或旋转，但不必凭空拥有法力和施法能力。元法术必须声明需要哪些组件；目标缺少组件时应返回失败，而不是散落大量隐式特殊逻辑。

## 拟议属性与当前对应

| 拟议属性 | 当前对应                    | 需要明确的语义                                   |
| -------- | --------------------------- | ------------------------------------------------ |
| 生命     | `hp` + `hpMax`              | 当前值与上限应分开；无 Vitality 时如何消失       |
| 法力     | `mana` + `manaMax`          | 当前值与上限应分开；非施法实体可无此组件         |
| 法力回复 | `manaRegen`                 | 单位仍建议是每秒数值                             |
| 神识上限 | `shenshiMax`                | 继续表示变量空间，不等于神识强度                 |
| 移动速度 | `speed`                     | 是最大速度、基础速度还是瞬时位移倍率             |
| 施法速度 | `castSpeed`                 | 是否影响所有动态 tick 成本                       |
| 术法威力 | `power`                     | 影响哪些控制效果，不应只等于伤害倍率             |
| 法力消耗 | `manaCostMul`               | 应影响法力而非时间；若也影响时间会与施法速度重叠 |
| 冷却时间 | `cooldownMul`               | 拟删除，需迁移法术注解和现有内容                 |
| 神识强度 | 当前无；拟替代 `perception` | 同时影响范围、成功率、成本还是抗性               |
| 肉体强度 | `armor`                     | 固定减伤、比例减伤或对不同伤害类型分别生效       |

“法力消耗决定所有元法术的时间”可能是表述笔误。若原意确实如此，需要重新命名，因为当前 `manaCostMul` 只影响法力，所有元法术的真实时间由 `castSpeed` 决定。

## 关于移除冷却

我倾向于赞成移除冷却：法力、施法 tick、同时只能维持一次施法、受击打断和实体创建上限本来就可以形成节奏。但移除前必须明确：

- 按住按键是否每帧重复起手，还是只响应按下边沿。
- 零法力、零 tick 的法术是否可能无限触发。
- duration/channel 结束后何时允许再次起手。
- AI 是否会以每帧频率尝试施法。
- 现有所有 `@cooldown` 法术和 `cooldownMul` 属性如何迁移。

建议不是简单删除字段，而是先用“触发边沿 + 最小执行 tick + 单实体施法互斥 + 资源不足反馈”替代它承担的保护职责。

## 需要先决定的问题

1. 强度元法术统一采用“请求效果”“投入法力”还是“效果 + 预算”？
2. 神识强度影响成功/失败、资源价格、最大距离，还是三者都影响？
3. 自身、己方所有物、友方和敌方实体是否使用不同控制成本？
4. 状态探查返回单属性、状态快照还是可组合的查询结果？
5. 控制或探查失败时返回 `bool`、`空`、实际完成量，还是直接使施法失败？
6. Projectile 的生命应是可受伤生命、固定寿命，还是两者都可以存在？
7. 每个施法者、每个法术或每类实体是否需要创建数量上限？
8. 肉体强度对所有伤害统一减免，还是先引入伤害类型？
9. 动态成本下，推演台必须承诺“全局上界”还是“指定场景上界”？

## 建议的实施顺序

1. 用 3 至 5 个目标法术反推最小能力集，例如可转向飞剑、蓄力弹、可减速弹道、护盾实体和远程夺取控制。
2. 决定统一实体/组件结构、句柄语义和失败返回值，形成 ADR。
3. 决定动态资源公式与静态分析契约，形成独立 ADR。
4. 先实现“创建 Projectile → 控制 Projectile → 查询 Projectile”的一个纵向切片。
5. 迁移现有元法术与默认法术，保留兼容层或一次性迁移工具。
6. 最后移除冷却，避免同时改变实体、计价和触发节奏而难以定位问题。
