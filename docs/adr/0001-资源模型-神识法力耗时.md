# ADR 0001：三种资源对应算法的三种复杂度

- 状态：已采纳
- 日期：2026-09-12

## 背景

游戏的核心理念是「用有限资源约束玩家的创造力，鼓励更优雅的实现」。
需要一个资源模型，能被玩家直觉理解，又能精确映射算法复杂度。
Noita 的 wand 是「组合数据」，本项目是「组合程序」，抽象层级更高，
因此必须让「程序写得好不好」这件事有可量化的代价。

## 决策

| 资源     | 语义             | 对应算法概念 | 计费点                               |
| -------- | ---------------- | ------------ | ------------------------------------ |
| **神识** | 持有状态的成本   | 空间复杂度   | 声明变量时占用，释放时归还，超限失败 |
| **法力** | 与外界交互的成本 | I/O 开销     | 只有「读世界 / 改世界」的元函数收费  |
| **耗时** | 执行步数         | 时间复杂度   | 元函数与下标运算计费，纯控制流免费   |

最关键的派生规则：

> **神识内运算（加减、比较、距离、取长度）几乎不要法力；
> 凡是「看一眼世界」或「改变世界」的操作都收高额法力。**

## 理由

这条规则让「批量 I/O vs 逐个 I/O」这一经典权衡自然涌现：

- 朴素：拿句柄后逐个查询 → 法力 O(n)
- 优化：一次批量读入神识 → 法力 O(1)，神识 O(n)

而且三者互相制衡，**不存在单一最优解**：
批量写法省法力但费神识；敌人少时朴素反而更省；
调小列表容量能省神识但会漏掉目标。

已用无头沙盒验证（`npm run sandbox`），三种写法在 1/3/8 敌人、三种境界下
各有胜负，取舍成立。

## 后果

- 元法术注册与定价（`src/core/metas/*.ts`）成为全局平衡核心，完整现状由 [`../reference/meta-spells.md`](../reference/meta-spells.md) 从代码生成
- 静态分析器必须与 VM **逐项对齐**（调用开销、循环开销都要计），
  否则「静态上界」会低于实测，玩家将不再信任消耗面板
- 后续新增元函数时，必须先归入「神识内 / 读世界 / 改世界」三类再定价
