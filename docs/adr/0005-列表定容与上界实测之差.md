# ADR 0005：列表定容，且刻意保留「上界 vs 实测」的差距

- 状态：已采纳
- 日期：2026-09-12

## 背景

列表长度在运行前未知，静态分析无法给出精确消耗。
最简单的做法是让列表动态增长、神识按实际长度计 —— 但那样
静态分析给出的数字会失去意义（永远等于最坏情况，且玩家无法优化）。

## 决策

1. **列表必须定容**：`list<元素类型, 容量>`，容量写进类型
   - 神识成本 = 1 + 元素价格 × 容量（容量即预算）
   - 感知类元函数返回动态容量列表，赋给定容变量时按容量**截断**
2. **静态分析按容量算上界，实际执行按真实长度算**
   - 这个差距**刻意保留**，不消除
3. 遍历列表的最坏消耗 = 容量 × 循环体

## 理由

把「容量」变成一个玩家可调的旋钮，产生三重取舍：

- 容量大 → 不会漏目标，但神识贵、静态上界高
- 容量小 → 神识省、上界低，但真实目标过多时会**看漏**
- 因此「把容量调到刚好够用」本身就是一种优化技巧

已验证：容量 4 的法术在 8 敌场景下神识只要 15（16 容量版要 39），
代价是打中了第 4 近的敌人而不是最近的。

## 后果

- 静态上界必然大于等于实测，这是**设计意图**，不是缺陷；
  但反过来（上界 < 实测）是 bug，有单测专门看守
- UI 上要同时展示「上界」与「实测」，并解释两者差异，否则玩家会困惑
- 后期若引入「不定容列表」，需要重新设计这块的静态分析
