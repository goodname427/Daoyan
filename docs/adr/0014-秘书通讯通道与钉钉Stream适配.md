# ADR-0014：秘书通讯通道与钉钉 Stream 适配

- 状态：已采纳
- 日期：2026-09-20

## 背景

制作人需要离开电脑后继续查看项目进度、发送自然语言和处理少量待办。手机版 Sites 在当前内嵌浏览器与移动网络下出现布局、交互和 TLS 兼容问题，但这些问题属于交互载体，不应迫使项目重做常驻秘书、版本状态或调度流程。

ADR-0012 已确定 notice guard 是事件驱动秘书的持久边界，但当时只落到 HTTP 与出站 webhook。钉钉 Stream 可以在不开放本机公网端口的前提下接收机器人消息，因此适合作为当前移动通讯入口。

## 决策

建立平台无关的 `SecretaryChannel` 边界：

1. 常驻秘书内核继续以 `.daoyan-agent/secretary/` 为唯一持久状态，负责收件、查重、排期、版本与通知事件。
2. Channel 只负责接收统一自然语言消息、发布统一秘书通知和管理自身连接生命周期；它不拥有任务队列或版本状态。
3. notice guard 只依赖 Channel 接口和通道工厂，不导入任何钉钉消息类型。
4. 钉钉适配器使用官方 Stream SDK 接收入站文本，以平台消息 ID 生成稳定收件 ID，并通过制作人 staffId 白名单限制入口。
5. 关联答复优先回到原消息会话；没有关联会话的任务完成、阻塞与待办通过机器人单聊接口主动通知。
6. 通道在本机收件与 HTTP 服务启动后于后台连接；配置、连接或发送错误不能中止本机秘书、PM 或其他通道。通知先进入持久 outbox，离线通道仍属于待发目标，并按恢复定时器重连和重试。
7. 平台凭据只由 notice guard 的运行环境提供，不写入仓库、状态文件、事件或日志，也不传递给语义 Agent、PM 或其执行子进程。
8. 外部 SDK 按配置动态加载；未启用的平台不能成为 notice guard 的启动依赖。

钉钉是第一个双向 Channel，不是秘书内核。未来企业微信、Slack、独立移动 App 或恢复 Sites，都应复用相同入站与通知契约；需要丰富卡片时在对应适配器中实现，不向状态机加入平台字段。

本 ADR 补充 ADR-0012 的通讯实现细节；ADR-0012 关于常驻秘书、Feature PM 和事件休眠的职责划分保持不变。

## 后果

- 移动交互方案可以独立替换，不会迁移项目队列或版本档案。
- 钉钉断线时本机中枢、CLI、HTTP 和项目开发仍可继续。
- 通知采用至少一次交付语义；极端情况下可能重复简报，但不会因一次网络错误永久丢失答复。
- Stream 长连接在空闲时占用网络连接，但不会触发模型调用，空闲 token 消耗仍为 0。
- 首次部署需要制作人在钉钉管理后台创建企业内部应用、启用 Stream 机器人，并提供 Client ID、Client Secret 与授权 staffId。
- 第一阶段使用文本消息；交互卡片和移动可视化属于适配器增强，不阻塞基础通讯闭环。

## 未选择方案

- **继续修补手机版 Sites 作为唯一入口**：当前问题同时涉及宿主布局与网络可达性，投入不能直接改善秘书通讯可靠性。
- **把钉钉作为第二套秘书状态**：会造成排期、回复和版本事实分叉。
- **让钉钉 SDK 进入 notice guard 状态机**：会把供应商类型扩散到核心流程，增加替换成本与故障范围。
- **自建公网入站网关**：需要额外域名、TLS、鉴权和持续运维；Stream 已满足当前双向通讯需求。
