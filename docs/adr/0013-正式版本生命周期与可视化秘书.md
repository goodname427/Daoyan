# ADR-0013：正式版本生命周期与可视化秘书

- 状态：已采纳
- 日期：2026-09-20

## 背景

现有 `producer:version` 只会从项目状态中冻结若干 Feature，再顺序调用 Feature PM。它具备恢复和交付能力，但没有版本立项、策划评审、范围冻结、版本测试、缺陷闭环与制作人体验，因此不能继续代表正式版本。

制作人同时需要一个可视化秘书，用来查看当前版本所处环节、进入每个节点阅读状态和证据、处理自己的待办，并通过同一个 notice guard 与秘书自然语言交流。

## 决策

引入独立于开发批次的正式版本生命周期。一个正式版本依次经过：方向、版本策划、制作人评审、模块策划、主策评审、任务拆分、版本排期、开发、版本测试、缺陷修复、候选构建、制作人体验和归档。

正式版本的持久状态保存在 `.daoyan-agent/releases/`，长期策划、测试与报告保存在 `docs/versions/<version-id>/`。状态节点只引用仓库内证据，不把大段文档复制进运行状态。

制作人评审版本策划案和最终候选版本是强制门禁；模块策划是否升级给制作人由主策决定。版本排期通过后冻结范围，新方向默认进入后续候选池。只有制作人明确改变当前版本承诺，才能修改冻结范围。

原 `version-dispatcher` 改称开发批次调度器，仅供 Version PM 在已批准计划的开发阶段调用。它不再创建正式版本，也不能绕过策划、测试或体验门禁。

可视化秘书由 notice guard 在本机提供 HTTP 页面和 API。页面只读取秘书与正式版本的持久状态；发送消息仍写入同一收件箱，由现有事件驱动流程处理。notice guard 空闲时仍不调用模型。

角色是按事件唤醒的专业 Agent，不是常驻模型：

- 常驻秘书维护总状态、对话、通知和阶段调度。
- 主策负责版本策划、模块边界与跨模块一致性。
- 策划负责详细策划和任务拆分。
- Version PM 负责依赖、优先级、工作量、范围冻结和版本收束。
- Feature PM 负责单项开发交付。
- 测试 Agent 负责版本测试、主线回归、缺陷登记和复验。

任何关键产物不得由同一 Agent 自产自审。审批记录包含评审者、时间、文档版本、结论与意见。

## 后果

- 自动推进只发生在已经批准的正式版本内部；系统不会把 `docs/status.md` 中的候选项自动包装成下一个正式版本。
- 制作人只在版本策划、被升级的模块策划、候选体验和真实阻塞时介入。
- 看板和命令行共享同一状态，不会产生第二套秘书队列。
- 正式版本完成与对外发布分离；大版本发布仍由制作人决定。
- 首个纵向切片先建立状态机、看板和对话闭环，再让后续专业 Agent 自动生产各阶段文档。

## 未选择方案

- **把看板嵌入游戏推演台**：项目管理与玩家体验属于不同产品边界，会污染游戏界面和打包产物。
- **继续扩展旧版本清单**：旧清单以 Feature 执行为中心，无法自然表达评审、策划和测试回环。
- **让网页直接修改 JSON**：会绕过 notice guard 的去重、恢复和安全边界。
