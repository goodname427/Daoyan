# ADR-0021：版本节点任务与 PM 分层

- 状态：已采纳
- 日期：2026-09-24
- 决策者：制作人（2026-09-24 对方案确认并要求实施）

## 问题

当前正式版本每个内部节点只派发一个 PM。开发节点把整版工作项直接变为同一 PM 的执行 Agent 任务，直到全部完成才汇总报告和提交。这与“一项具体交付由一个 Feature PM 负责”的职责定义冲突；任务拆分、排期两个独立节点还提前决定了 Feature PM 内部的实现步骤。若仅把一个节点复制成多个 PM，现有每个 PM 均运行完整门禁的合同会在后续提交改变代码树时失效，产生重复测试和错误复用风险。

## 决策

1. 一个正式版本由一个**逻辑上的 Version PM** 贯穿。它在每个可执行节点进入时，根据已批准的产品意图、上一节点结果和当前范围修订，按需建立零到多个有界交付任务，声明稳定 ID、交付物、验收、依赖、建议读取路径和独占写入范围。它只决定该节点交付什么及顺序，不替 Feature PM 拆调研、实现、测试等内部步骤。执行可分多次事件驱动调用；持久版本状态而非无限模型对话承载连续性。
2. 每个节点任务交给一个 Feature PM。这里的 Feature 指可独立检查与提交的有界交付物，也可以是策划、测试或候选材料，不限于玩家功能。Feature PM 在任务合同内自主规划内部执行 Agent、验证和修复，并提交独立结果。制作人门禁不创建 Feature PM。测试和设计审核须与所验收产物的作者身份分离。
3. 常驻秘书只管理跨版本入口、查重、队列、事件、进程占用、结构化证据和通知。它不拆节点任务、不读完整任务历史、不替制作人决定方向。Version PM 负责节点任务合同和阶段验收；Feature PM 负责单项交付；执行 Agent 只负责内部子任务。
4. 新正式版本保留方向、版本策划、制作人立项评审、详细策划、设计评审、开发、版本测试、缺陷修复、候选构建、制作人体验和归档。取消独立的任务拆分和版本排期节点。版本范围在获批策划与设计评审后冻结；节点任务在各节点进入时才细化。旧版本保持原节点和证据只读，不重写历史。
5. 同一集成工作区默认只有一个写进程。只读研究与审查可以并行。任务声明写入范围，调度器按实际变化复核；越界、重叠或过期输入不得静默接纳。共享阶段报告与 `docs/status.md` 由 Version PM 在阶段收束时统一写。
6. 执行 Agent 只做直接检查。Feature PM 对自身任务做风险相称的定向/快速门禁与独立审查，在版本集成分支形成独立提交。整版集成后的最终代码树由版本验证责任者运行一次 `npm run verify:full`；Version QA 只复用与树、修订、命令和配置相匹配的证据并补跨 Feature 验收。代码、测试、输入策划或验证配置变化使证据失效，修复后对新树重跑。提交可以先形成，但未经整版完整门禁不得推入主干或宣布版本交付。
7. 交接只传带来源、修订及指纹的任务合同和直接依赖公开结论，不复制完整 Agent 记录。独立审查自行读取合同与实际差异；必要的重复验证不能省略。问题优先退回原 PM 及恢复点，仅失效受影响任务和下游证据。

## 后果与兼容

版本生命周期要增加节点任务与任务级 PM 运行身份，修改秘书派发、恢复、阶段验收、Git 和验证证据。新合同不能通过只改提示词实现。旧归档版本继续按原模式读取；活动旧版不能在中途无损切换，应停在原模式直至完成或显式迁移。当前没有活动正式版本。此控制面改动不创建新正式版本。

先保证串行写入与完整证据；隔离工作树并行写入只在真实测得收益且能证明冲突检测后另议。增加任务、节点级调用数、已知 token、重复读取与同树门禁次数的观测，以验收质量、返工和总成本共同评估。
