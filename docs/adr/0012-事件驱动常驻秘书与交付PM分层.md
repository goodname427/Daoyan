# ADR-0012：事件驱动常驻秘书与 Feature PM 分层

- 状态：已采纳
- 日期：2026-09-14

## 背景

现有 `producer` 与 `producer:version` 能完成一次 feature 或一个有界版本，但它们在交付后退出。制作人的新想法无法在当前工作运行时可靠查重、排队，也没有一个跨版本生命周期的角色在完成节点主动通知制作人。让一个模型进程永久轮询可以解决表面问题，却会持续消耗 token，并把项目组合管理和代码交付再次混到同一个上下文中。

## 决策

建立三层职责：

1. **常驻秘书**维护项目组合状态，处理自然语言消息、查重、排期、完成通知和持续推进。
2. **Feature PM**继续由 `producer` 与 `producer:version` 承担，负责单个 Feature 或版本的拆分、模型路由、恢复、验证、审查和 Git 收束。
3. **执行 Agent**只承接 PM 分配的独立实现或审查任务。

常驻秘书由仓库外层的 deterministic `notice guard` 承载。它只监听文件系统消息、HTTP 请求、子进程退出和已登记的恢复定时器；没有事件时阻塞休眠，不调用模型，因此空闲 token 消耗为 0。制作人消息到达后，guard 才短暂调用低成本语义 Agent；若模型不可用，则以本地保守规则查重并继续落盘，不能丢消息。

`.daoyan-agent/secretary/` 是秘书的持久真相，保存收件箱、队列、当前运行、恢复时间、答复和通知事件。代码事实仍以代码、测试和 `docs/status.md` 为准，秘书状态不能覆盖仓库事实。

Feature PM 在 Feature 恢复点和版本清单中记录当前进程标识。guard 重启后只会挂接仍存活的已知进程，确认原进程退出后才自动恢复；无法确认进程归属的旧格式运行保持观察并请求接管决定，不能冒险启动第二个写进程。

每个执行任务通过后，Feature PM 在恢复点写入稳定任务 ID、标题和完成时间。notice guard 由文件事件唤醒，读取任务的 Feature/版本父级与运行目录，将完成节点先记入持久状态，再发送简短的 `task-complete` 事件。稳定键由运行目录和任务 ID 组成，guard 重启后不会重复通知。该结构同时是未来任务可视化界面的只读数据源，不要求常驻模型参与进度汇报。

Feature 或版本完成后，秘书通知制作人并继续队列；队列为空时从项目状态承接下一项，没有待办才休眠。产品冲突、不可逆决策、大版本发布、额度或鉴权阻塞会暂停并通知制作人；制作人的下一条自然语言回复用于恢复原任务。消息和 Feature/版本范围均由秘书判断，通讯入口不传类型标记。

通讯软件通过 notice guard 的 HTTP 收件口和出站 webhook 接入。仓库只定义协议和飞书、企业微信、Discord、通用 JSON 适配，不保存平台凭据，也不绑定单一通讯产品。

## 后果

- 空闲时只有一个事件监听进程，不发生模型调用；模型成本与实际消息和交付事件相关。
- 项目队列可跨终端、Agent 会话和主机进程重启恢复。
- Feature PM 保持有界、可测试，不承担无限版本生命周期。
- notice guard 是本机常驻进程；主机重启后需要由系统登录项、进程管理器或人工运行 `npm run secretary:start` 拉起。
- 通讯软件的入站机器人仍需在平台侧配置 webhook 转发或网关，凭据属于部署配置。

## 未选择方案

- **常驻模型轮询**：空闲仍产生费用，且长上下文会不断漂移。
- **让 `producer:version` 无限吸收新任务**：破坏版本队列冻结和 Review 节点，单次失败也会拖垮整个项目生命周期。
- **直接绑定某个聊天平台 SDK**：增加凭据和供应商耦合，且不利于本地开发与测试。
