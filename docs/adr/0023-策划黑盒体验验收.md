# ADR-0023：开发后增加策划黑盒体验验收

状态：已采纳（2026-09-27）

## 背景

详细策划与主策审核发生在开发前，开发自测和版本 QA 主要验证实现、集成与回归。它们不能独立证明玩家在游戏里得到的行为符合已批准策划，尤其容易漏掉制作人未逐一列举的相邻玩法。等制作人体验候选版本才发现方向偏差，返工成本过高。

## 决定

在开发集成完成后、版本 QA 前增加“策划体验验收”。未参与该功能实现的主策或策划先阅读已批准的模块方案，再以玩家身份运行游戏。每项实际开发成果至少覆盖主流程和边界流程，整个版本至少覆盖一个相邻情形；每项保留策划出处、入口、操作步骤、预期、实际观察和可核查的运行证据，绑定开发代码修订。黑盒体验不读取实现来推定规则，不用单元测试或开发自述代替操作。

Version PM 只拆当前节点的有界体验任务并汇总结论，Feature PM 组织独立策划执行；策划与主策对玩法一致性作出结论。若体验与策划不符，记录具体偏差并回到开发修正，再重新策划验收；不能修改策划以迁就实现。若策划本身出现未批准的产品方向冲突，按既有主策与制作人决策门禁对齐。通过后才进入独立版本 QA。纯文档版本可按明确阶段策略跳过。

验收阶段只写本版本证据，不改产品实现、游戏测试或已批准策划。开发最终树已有的一次完整门禁继续复用；策划体验与版本 QA 分担不同职责，不重复完整门禁。历史已归档或已进入 QA 的旧版不补记“通过”；尚未走到开发完成的 v2 正式版本在读取时由生命周期内核补入待执行节点与执行策略，随后由正常版本写入持久化，不手工编辑状态文件。

## 取舍

- 多一个内部节点，会增加一次真实游戏体验的时间，但在制作人候选体验前暴露玩法偏差。
- 策划体验需要可运行宿主与真实证据；环境不支持时停在技术阻断点，不能用纸面审查或代码门禁冒充体验。
- 策划验收通过只证明与批准方案的玩家表现一致，版本 QA 仍需验证跨功能集成、回归和缺陷复验。
