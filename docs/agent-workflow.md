# 制作人工作流

这套流程让制作人只负责方向。事件驱动的常驻秘书负责跨 feature/version 的项目现状、收件、排期和通知；`producer` 与 `producer:version` 是单次交付 PM，负责理解、分派、验收和 Git 收束。模型选择和任务复杂度是执行层问题，不是制作人的输入要求。

## 三层职责

| 层级                    | 生命周期            | 职责                                           | 空闲成本   |
| ----------------------- | ------------------- | ---------------------------------------------- | ---------- |
| 常驻秘书 / notice guard | 跨版本              | 查重、队列、唤醒、恢复时间、通知与 Review 暂停 | 0 token    |
| 交付 PM                 | 一个 feature 或版本 | 拆分、模型路由、门禁、独立审查、修复与 Git     | 运行时计费 |
| 执行 Agent              | 一个独立子任务      | 实现、聚焦测试或审查                           | 运行时计费 |

常驻不等于常驻模型。外部 notice guard 使用文件事件、HTTP 请求、子进程退出和单次恢复定时器阻塞监听；只有事件到达才短暂唤醒语义 Agent。该边界由 [ADR-0012](./adr/0012-事件驱动常驻秘书与交付PM分层.md) 固定。

## 最常用方式

在 Codex 主任务中直接描述目标或体验问题，例如：

> 我希望推演台可以单步执行法术，并看到每一步的变量和资源变化。

不需要补充“这个任务复杂吗”“该用哪个模型”“怎么拆分”或测试命令。当前主 Agent 应自动作为秘书完成后续工作，只在产品方向冲突、不可逆选择或大版本发布时请求决定。

本机常驻入口：

```bash
npm run secretary:start
npm run secretary -- "我希望法术可以组合出持续护盾"
npm run secretary:status
```

`secretary` 会自动启动未运行的 guard。精确命中 `docs/status.md` 或正在运行清单时直接答复，不创建重复任务；新方向进入持久队列，当前 PM 结束后再启动。版本方向使用：

```bash
npm run secretary -- --version "推进到下一个稳定可玩版本"
```

秘书明确请求产品取舍后，用同一入口回复并标记为决策；它会把内容送回原恢复点，而不是新建任务：

```bash
npm run secretary -- --decision "采用方案 A，兼容已有存档"
```

停止本机 guard：

```bash
npm run secretary:stop
```

## 秘书交付循环

```text
制作人方向
→ 秘书读取项目事实并建立任务合同
→ 自动拆分和选择模型
→ 执行者顺序交接并按失败升级
→ 固定完整门禁
→ 独立审查与自动修复
→ 文档、提交和推送
→ 向制作人汇报体验结果
```

秘书必须对最终结果负责，不能把 Agent 的中间报告未经验证地转交给制作人。一个模型能可靠完成时不拆分；拆分只用于隔离上下文、不同专业领域或明确依赖阶段。

## 自动路由

| 风险层级   | 使用场景                                     |
| ---------- | -------------------------------------------- |
| `economy`  | 文件检索、参考生成、格式整理和机械性文档     |
| `standard` | 常规功能、React/CSS、普通缺陷、单元与 E2E    |
| `advanced` | `src/core/`、DSL、编译器、VM、并发、共享契约 |
| `critical` | ADR、架构不变量、不可逆迁移和重大版本审计    |

执行失败会先区分临时基础设施故障与任务失败。容量不足、网络抖动和超时会先在原模型重试；仍不可用时，执行任务向更高层级接管，独立审查和审查修复则按策略切换备用模型。同一风险层级的线性任务会自动压缩成一个执行者，避免重复读取上下文。调度器最多创建配置允许的任务数和修复轮次，避免失控消耗。

当前策略见 [`../agents/policy.json`](../agents/policy.json)。调整模型不需要修改调度器代码。

默认规划由本地规则完成，不调用模型，也不产生 token。它会识别纯文档、常规体验、核心语义和不可逆架构信号；同时涉及 Core 与 UI 时自动拆成 Sol 和 Terra 两段。只有秘书确实需要第二意见时才使用 `--deep-plan` 调用低成本规划模型。

“继续”“下一步”“继续推进后续的开发任务”等纯续作方向会先解析为 [`status.md`](./status.md) 的“当前首要任务”或“下一阶段候选”第一项，再进行本地路由。制作人仍可用任何更具体的新方向覆盖它。这样执行者不会为了猜测“后续”而重新遍历整个仓库。

## 命令入口

通常由 Codex 主 Agent 在内部使用，制作人无需操作。需要查看秘书会如何拆分而不修改代码时运行：

```bash
npm run producer:plan -- "增加法术单步推演和变量观察"
```

这些 `producer*` 命令是交付 PM 的底层入口。日常方向优先交给 `secretary`，这样新消息可以在已有工作运行期间排队，不会打断当前 feature。

## 通讯软件接入

notice guard 可选开启本机 HTTP 收件口：

```powershell
$env:DAOYAN_SECRETARY_HTTP_PORT = "17321"
$env:DAOYAN_SECRETARY_TOKEN = "<local-secret>"
npm run secretary:start
```

通讯机器人或网关向 `POST /intake` 发送：

```json
{ "idea": "增加持续护盾法术", "scope": "feature", "decision": false }
```

使用 `Authorization: Bearer <local-secret>`；`GET /status` 返回脱敏后的项目组合状态。服务默认仅绑定 `127.0.0.1`；若显式绑定非本机地址，notice guard 会强制要求设置 token。公网接入应由已有机器人、反向代理或隧道负责认证和 TLS。

出站通知设置 `DAOYAN_SECRETARY_WEBHOOK_URL`，并通过 `DAOYAN_SECRETARY_WEBHOOK_KIND=generic|feishu|wecom|discord` 选择载荷格式。凭据只放环境变量，不提交仓库。没有 webhook 时，事件仍写入 `.daoyan-agent/secretary/events.jsonl`。

语义查重默认仅在新消息到达时调用 `agents/secretary.json` 指定的低成本模型。设置 `DAOYAN_SECRETARY_LOCAL_ONLY=1` 可完全禁用该调用，使用本地保守查重；无论哪种模式，空闲期间都不会调用模型。

让秘书完成规划、实现、验证、审查、提交与推送：

```bash
npm run producer -- "增加法术单步推演和变量观察"
```

`producer` 的交付单位是一个 feature。当制作人给出的是一个版本目标，希望秘书持续从 [`status.md`](./status.md) 推进多个 feature 直到可 Review 节点时，使用：

```bash
npm run producer:version -- "推进到下一个稳定可玩版本"
```

先只看本次会冻结哪些 feature：

```bash
npm run producer:version:plan -- "推进到下一个稳定可玩版本"
```

版本调度不会把所有需求塞给同一个 Agent。它在开始时按优先级冻结有上限的 feature 队列，再为每一项独立调用完整 `producer` 闭环。每轮都必须验证、独立审查、提交并更新 `status.md`；上一轮交付后才会进入下一轮。队列完成后再运行一次跨 feature 完整门禁，然后将状态标记为 `review-ready`。
默认一次最多两个高层 feature；`--max-rounds` 只能减少轮数，不能超过策略上限。

版本运行中的 feature 失败时，外层秘书先普通续跑，仍失败再使用强制接管，不立即把中间故障丢给制作人。只有需要产品决策、自动恢复次数耗尽或外部条件持续不可用才暂停。暂停后不需重新描述目标：

```bash
npm run producer:version:resume -- ".daoyan-agent/versions/<运行目录>"
```

如果是因产品决策暂停，制作人给出决定后直接附在同一条恢复命令后，不用新建版本任务：

```bash
npm run producer:version:resume -- ".daoyan-agent/versions/<运行目录>" "采用方案 A，保留现有存档兼容"
```

如果当前工作区已经有执行 Agent 遗留的部分改动，且制作人决定让秘书直接接管现场：

```bash
npm run producer -- --takeover "继续完成动态资源预算"
```

`--takeover` 会在本次运行目录写入 `takeover.json`，记录接管原因、基线提交、工作区指纹、改动清单和未跟踪文件清单；执行者必须保留并审查相关遗留改动，秘书最终仍负责验证、审查和 Git 交付。

网络暂不可用但仍希望完成本地交付和提交：

```bash
npm run producer -- --no-push "修复推演台滚动问题"
```

完整执行要求开始时 Git 工作区干净，防止自动提交混入来源不明的改动。若检测到上一执行 Agent 已建立恢复点、尚未完成首个任务且异常退出，秘书会自动审查并接管其遗留改动；其他脏工作区可由制作人显式使用 `--takeover` 接管，不能把是否安全交给制作人判断。`producer:plan` 是只读分析，可以在脏工作区运行。

需要诊断本地路由，或方向非常模糊而必须让模型提供第二意见时，秘书可以运行：

```bash
npm run producer:plan -- --deep-plan "重新考虑整个实体与资源架构"
```

该选项会消耗额外 token，不是制作人需要选择的常规入口。

若完整入口在启动 Codex 或 npm 时失败，可运行不消耗 token 的环境诊断：

```bash
npm run producer:doctor
```

临时故障会在当前进程内自动重试和换模型，制作人不需要操作。若账号额度、登录或持续性服务故障导致进程最终停止，修复外部条件后可从原运行目录续跑：

```bash
npm run producer:resume -- ".daoyan-agent/runs/<运行目录>"
```

如果恢复点的工作区指纹已经变化，但当前现场就是需要保留的遗留改动：

```bash
npm run producer:resume -- --takeover ".daoyan-agent/runs/<运行目录>"
```

强制恢复会记录新的 `takeover.json`，放弃旧的任务跳过记录并从该运行的完整任务合同重新执行；它不会静默把不一致现场当成已完成。

续跑会读取 `recovery.json`，先核对 `HEAD`、已跟踪差异和未跟踪文件内容组成的工作区指纹。指纹一致才会跳过已完成任务，从验证、审查、修复或 Git 交付阶段重新接管。若提交已创建但推送中断，它会继续推送该提交，不会重复提交。若上一次 Agent 在首个任务中异常退出，秘书会放弃旧的跳过记录，审查当前遗留改动后重新执行完整任务；其他指纹不一致仍拒绝续跑，防止将外部改动混入自动提交。

## 自动执行边界

秘书会自动决定：

- 是否需要规格或 ADR；
- 是否拆分任务以及各任务模型；
- 实现、测试、文档、提交和推送；
- 验证失败后的修复与模型升级。

秘书必须询问制作人的情况：

- 两种产品体验方向互相冲突，仓库事实无法决定；
- 将改变已经采纳的核心架构不变量且没有明显可回退路径；
- 即将进行大版本发布；
- 需要制作人提供外部账号、凭据或无法自行取得的素材。

普通技术取舍、模型选择、文件组织、测试范围、普通 tag 和是否推送不应打断制作人。

## 运行记录与恢复

每次执行在 `.daoyan-agent/runs/<时间-方向>/` 保存：

- `plan.json`：模型原始计划；
- `plan.validated.json`：通过本地校验的任务合同；
- 每个任务的最终消息和完整日志；
- `verify-*.log`：交付门禁输出；
- `review-*.json`：独立审查结果；
- `review-input-*.patch`：由父进程生成、供审查者聚焦读取的完整差异；
- `progress.json`：当前阶段、开始时间、更新时间和已运行秒数；
- `recovery.json`：当前基线、工作区指纹、已完成任务、token 计数、审查结果和可续跑阶段；
- `report.md` 与 `report.json`：最终状态。

报告同时记录规划、执行和审查调用可取得的 token 用量，便于按真实通过率和消耗调整 [`../agents/policy.json`](../agents/policy.json)，而不是凭感觉长期使用最强模型。

多轮版本运行另存于 `.daoyan-agent/versions/<时间-目标>/`：`version.json` 是可恢复的队列真相，`feature-*.log` 聚合各轮终端输出，`verify-full.log` 是最终跨 feature 门禁，`report.md` 是制作人 Review 入口。每个 feature 仍在 `.daoyan-agent/runs/` 保留自己的计划、差异、审查和恢复证据。

跨版本的常驻秘书另存于 `.daoyan-agent/secretary/`：`state.json` 是队列真相，`inbox/` 与 `responses/` 是可靠收件协议，`events.jsonl` 是待通知历史，`notice-guard.log` 和每项任务日志用于诊断。notice guard 重启时会接管已有的未完成版本或 feature；外部额度阻塞只登记一次恢复定时器，不循环唤醒模型。

长阶段每 20 秒在终端输出一次心跳并更新 `progress.json`。当前默认上限按风险分层：执行 4/6/12/18 分钟，审查 3/4/8/12 分钟，修复 4/6/10/15 分钟；完整门禁上限 10 分钟。超时会停止该子进程，普通执行仍可按既有策略升级一次。CLI 暂不提供调用中的硬 token 上限，因此“聚焦输入 + 较低模型层级 + 时间上限 + 事后 token 记录”共同承担成本控制。

执行者只运行聚焦测试和 `npm run verify`；`npm run verify:full` 由秘书统一运行，避免工作 Agent、审查者和父进程重复做同一轮完整门禁。审查者只读取预生成差异包及必要的直接契约，不运行命令，也不扫描无关文档与历史。超大差异和未跟踪二进制文件只记录清单与大小，不整块注入模型上下文。

该目录已被 Git 忽略。容量、网络和超时故障由秘书在当前运行中自动恢复；进程级中断后使用恢复点续跑。即使执行 Agent 已经写入部分文件但没有留下完整任务记录，秘书也会通过受控恢复点接管，不应让制作人重新描述整个需求。若自动识别不足，制作人只需在原方向或原运行目录上追加 `--takeover`，不需要手工清理现场或重新拆分任务。

## 当前限制

- 第一版按依赖顺序在同一个干净工作区执行，不让多个 Agent 同时编辑相同文件。后续只有在文件所有权和合并策略可靠后才开放并行 worktree。
- Codex CLI 必须已经登录，并支持 [`../agents/policy.json`](../agents/policy.json) 中配置的模型。
- 如果账号未登录、额度用尽或所有备用模型持续不可用，秘书无法在单个 CLI 进程内消除外部阻塞；此时会保留恢复点，而不是丢失已完成工作。
- 时间上限能够约束失控运行，但不能保证精确 token 预算；一次调用可能在超时前已经产生较大上下文消耗。
- 自动测试与独立审查不能替代产品体验。涉及 UI 时，当前主 Agent仍需启动应用并实际走完受影响路径，再向制作人交付。
- routine 任务不创建 tag；版本发布继续使用 `npm run release`，大版本发布必须由制作人决定。
- 版本队列是开始时的有界快照，不会在同一次运行中无限吸收新候选；新发现会写回 `status.md` 留给下一个版本运行。
- notice guard 是本机进程，系统重启后需由登录启动项、进程管理器或 `npm run secretary:start` 拉起；持久队列不会因此丢失。
- 仓库提供聊天平台无关的 HTTP/webhook 边界，但平台机器人、公网入口、凭据和 TLS 仍属于部署配置。
