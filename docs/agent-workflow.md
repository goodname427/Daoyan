# 制作人与常驻秘书

项目只保留一种日常工作范式：**制作人只和常驻秘书对话，秘书负责其余工作。**

制作人提供产品方向、体验反馈和大版本发布决定，不判断任务复杂度，不拆任务，不选模型，不指定测试，也不管理 Git。秘书维护跨 Feature、跨版本的长期队列和项目现状，再按正式版本阶段调度主策、策划、Version PM、Feature PM 和测试 Agent。

## 日常使用

直接在当前 Codex 对话或已绑定的钉钉机器人中描述想法即可，例如：

> 我希望推演台能对比两次法术测试的资源曲线。

两种入口进入同一份秘书队列和版本状态，钉钉只是移动端通讯 View，不拥有独立排期。需要从本机终端投递或诊断时，使用下面的后备入口：

```bash
npm run secretary -- "我希望推演台能对比两次法术测试的资源曲线"
```

常驻守卫未运行时会自动启动。首次部署也可以显式启动：

```bash
npm run secretary:start
npm run secretary:open
```

`secretary:open` 打开本机项目中枢。制作人可以切换当前和历史正式版本，查看版本环节及全部关联文档，检查运行中、休眠、等待或暂停的 Agent 及其可审计上下文，直接处理自己的待办，并在同一页面与秘书交流。历史版本只读。

查看当前正在做什么、排期和最近完成节点：

```bash
npm run secretary:status
```

当秘书确实需要产品取舍时，直接像正常对话一样回答：

```bash
npm run secretary -- "采用方案 A，兼容已有存档"
```

询问进度、增加方向或要求继续也完全相同：

```bash
npm run secretary -- "现在法术系统做到哪一步了？"
npm run secretary -- "继续按当前排期推进"
```

“继续”不是礼貌性确认：秘书必须把它关联到当前运行或第一项已批准排期。处于延时恢复的任务会改为立即重试并启动 Feature PM；已经运行时会明确回复对应任务；没有可执行排期时会说明正在等待新方向，不得承诺并未发生的推进。

制作人不需要标记这句话是问题、回复、Feature 还是版本。秘书结合近期对话、当前等待事项、运行状态和项目文档自行判断；无法立即回答的开发方向进入队列，能回答的问题会直接回复。消息与答复会持久保存，守卫重启后仍能延续上下文。

新方向只在确定为 `direction` 后进入正式版本去向判断：没有活动版本时建立待策划与立项评审的草案；未冻结版本内的同范围方向形成新的范围修订；可能改变已批准承诺的方向进入范围评审；冻结后进入下一版本候选。问题、无目标回复和“继续”分别只答复、保留或恢复已批准工作，不会据此建立空版本。每条收件的意图、去向、目标版本、范围修订和公开理由写入秘书 v1 编排扩展，重放同一请求不会重复操作。

语义判断关闭、失败或超时时，本地规则只路由明确方向；带标点或补充致谢的普通回复仍是回复，无法确认的输入保存为 `needs-confirmation`，不进入执行队列。即使句子同时包含“继续”或“恢复”，只要出现不要、不再、改成、不兼容、删除、替换、扩展等承诺变化，就必须先作为新方向进入范围判断。词面相似度只能关联主题，不能证明承诺未变化：首次立项评审前的草案可以合并，评审阶段及之后除同一原文方向外，未冻结范围增量保守进入 `scope-review`，删除、否定、替换和扩展均不能沿用旧批准。

制作人无需使用 `producer*` 命令。它们是 Version PM 和 Feature PM 的内部批次交付与故障恢复工具，见 [`operations/feature-pm.md`](./operations/feature-pm.md)。

已有等待制作人的事项不代表下一条消息必然是回复：明确新方向仍按版本范围路由，等待上下文仍可进行语义判断；新方向中的“确认”“审批”等词不构成对旧门禁的批准，不能把无关方向写入旧事项的制作人指导或恢复旧任务。

## 角色定义

新方向在事实查重入口只复用同一原文承诺。运行、队列或已完成记录的主题相似不能吞掉取消、禁止、替换或扩展请求；非同一方向继续按冻结状态进入范围评审或下一版本候选，语义判断的主题关联也不能替代这道门禁。

| 角色       | 生命周期          | 负责什么                                              |
| ---------- | ----------------- | ----------------------------------------------------- |
| 制作人     | 项目全程          | 定方向、评审立项、体验候选版本、决定大版本发布        |
| 常驻秘书   | 跨 Feature 和版本 | 唯一对话入口、总状态、调度、待办、问答和通知          |
| 主策       | 一个正式版本      | 版本策划、模块边界、策划审核和跨模块一致性            |
| 策划       | 一个模块或阶段    | 详细策划、规则边界、验收与任务拆分                    |
| Version PM | 一个正式版本      | 依赖、优先级、工作量、范围冻结、测试收束和候选构建    |
| Feature PM | 一项 Feature      | 任务合同、Agent 分派、验证、独立审查、恢复和 Git 交付 |
| 测试 Agent | 一个测试阶段      | 版本验证、主线回归、Bug 登记与复验                    |
| 执行 Agent | 一个小任务        | 实现或审查指定范围                                    |

“秘书”只指常驻秘书。旧文档中负责单次 Feature 的“秘书”统一称为 **Feature PM**。

执行效率按唯一作用域分责：执行 Agent 仅保留 Task 的直接检查证据；Feature PM 汇总后运行一次快速门禁、组织独立审查，并在最终代码树唯一执行 `npm run verify:full`、保留一份 Feature scope 完整门禁证据；Version QA 只消费仍匹配的该事实，再负责跨 Feature 集成、主线回归、迁移、打包和候选验证，不得重复生成完整门禁证据。候选代码令该证据失效时，必须回到 Feature PM 重建。证据以作用域、Git tree、命令和配置指纹复用；恢复不因无关树变化清空任务，而是只失效受影响任务及其下游。公开活动 ID 包含执行轮次和代码修订，统计分开显示模型计算、命令执行、等待制作人、等待额度、恢复和空闲时间；旧记录未知值保持不可用。

## 汇报节奏

常驻秘书只发简短摘要，详细信息保留给项目中枢：

- 收到方向：说明已完成、正在做、已排期，或已经加入队列。
- 小任务完成：报告任务标题及所属 Feature 或版本。
- Feature 完成：报告可体验结果，并自动继续当前版本排期。
- 版本策划完成：通知制作人评审，收到自然语言回复后继续或退回主策。
- 候选版本完成：通知制作人体验；通过后归档，反馈则进入修复回环。
- 需要决定：说明具体产品冲突；普通技术故障由系统自动恢复，账号、额度或外部访问阻塞则暂停并通知。

每个小任务事件都持久记录任务标题、父级、版本、完成时间和运行目录。守卫重启后按稳定任务键去重，不重复汇报；近期制作人消息和秘书答复也保存在状态中供后续对话使用。详细状态位于 `.daoyan-agent/secretary/state.json`，事件历史位于 `.daoyan-agent/secretary/events.jsonl`，具体运行证据位于事件中的 `runDirectory`。

项目中枢中的 Agent 数量只统计真实存活的执行进程；notice guard 空闲时显示休眠而不是执行中。桌面工作台顶部保留基础状态栏，左侧统一选择正式版本、流程节点、Agent、开发任务和版本缺陷；中间是 VS Code 式单一阅读区，每次只显示所选条目的节点详情与文档、Agent 持续公开记录，或任务/缺陷详情；右侧保留制作人待办和常驻秘书对话。三栏可拖动调宽、折叠和恢复；左、右栏内部的工作区区域还可独立折叠、调高和拖动排序，偏好只保存在当前浏览器。窄屏则以流程、详情、控制台导航切换，不启用区域高度拖动。Agent 记录只展示任务输入、结构化计划所产生的公开阶段、动作、修改文件、测试、错误和截断输出，不展示模型私有推理，也不以模态框打断阅读。制作人待办可以一键采用秘书推荐方案，也可以选择备选方案并补充说明；额度类临时阻塞默认登记恢复时间自动重试。

Feature PM 在运行目录写入 `public-events.jsonl`：字段按 input、plan/progress、action、file、test、error、decision、blocker、usage 分类别白名单投影，绝不接收私有推理或完整原始模型输出；未知 token 保持为不可用。看板只把持久公开事件与 `progress.json` 心跳、恢复点中的明确调度状态合并，不读取或按关键词猜测任何原始模型 `.log` 内容。旧运行缺少结构化公开事件时明确显示证据不可用，不能把原始输出重新解释为公开活动。

Feature PM 需要产品决定时，必须先写入 `waiting-producer` 恢复快照再退出。notice guard 将该状态恢复为制作人待办并停止自动重试；只有制作人对同一等待快照作出回复后，才携带决定从原恢复点继续。`recoverable` 只表示技术故障的可恢复中止，不能代替产品决策状态。

制作人决策待办通过 `decisionGateId` 关联具体门禁，看板批准或退回只解决该决策，不替代立项评审或直接推进阶段。每次对话决策还以请求 ID 写入门禁的去重历史；即使在“版本已写、回复未写”之间中断，重放也只恢复原答复，不会批准下一个门禁。拒绝不可逆决策或升级策划后，版本保持阻断并生成关联原门禁的重新审批待办，直到该门禁取得新的明确批准；拒绝范围增量则保留原有承诺。独立缺陷复验必须同时关联缺陷 ID、当前修复轮次、代码修订及范围修订，缺陷重新打开或重新修复后不能复用上一轮结果。

Feature PM 的执行与修复 Agent 按风险等级分别有 12、25、40、60 分钟的时限，仍每 20 秒写入心跳、进程身份和存活状态；因此正常的长任务会持续可观察，而只在其所属等级超时后才会被恢复流程中断。规划、审查和交付验证使用独立时限，避免把它们误判为执行 Agent 超时。

## 休眠与唤醒

常驻秘书由外部 notice guard 承载，不让模型永久运行。它只在以下事件到达时被唤醒：

- 制作人提交消息；
- PM 写入任务、Feature 或版本进度；
- PM 子进程退出；
- 已登记的恢复时间到达；
- 通讯网关收到外部消息。

没有事件时进程阻塞休眠，不轮询项目，也不调用模型，因此空闲 token 消耗为 0。语义 Agent 只在新的人类消息需要查重或澄清时短暂运行；任务完成通知由结构化状态直接生成，不消耗模型 token。

重试定时器只在全队列对账完成且派发未被阻塞后，为队首待执行事项安排。到期重试遇到待决事项、存活写进程或禁止派发时保留原恢复时间并休眠，等待回复、待办处理、进程退出等事件重新对账；单项快照对账不得反复挂零延时定时器。

既有运行快照缺失、损坏或状态不可识别时，保留运行目录、轮次与进程引用，记录 `missing` 对账阻塞并停止整队列派发。它保持跟踪状态并清除重试定时，普通确认或“继续”不能解除；内部恢复证据并核实 PM/子 Agent 归属及终态后，由下一事件重新对账。工作区干净不能证明运行未完成，Feature 缺少恢复文件也不能降级为新运行启动。

## 自动边界

运行等待保存具体快照标识（目录、运行 ID、轮次、状态、更新时间与阻塞内容）。制作人回复或看板恢复操作只确认该快照；确认与重试时间一起持久保存，重启对账不能把同一快照重新变成待办。新轮次或变化后的阻塞仍需再次处理，存活写进程、缺失证据及已交付终态仍优先阻止重派。旧等待记录首次处理前先补做快照对账，不从历史指导文字推断批准。

秘书和 Feature PM 自动决定拆分、模型、实现、测试、文档、提交、推送和普通 tag。只有以下情况会停下来询问制作人：

- 产品体验方向发生真实冲突；
- 不可逆地改变已采纳的核心架构；
- 大版本即将发布；
- 缺少必须由制作人提供的外部账号、凭据或素材。

正式版本内部各阶段和 Feature 完成后，秘书会继续已批准排期。只要当前版本没有制作人待办、账号额度或外部访问阻塞，notice guard 就必须在每次收件、Agent 退出、恢复定时器和状态变更后继续推进：自动跳过已声明不适用的节点，或为当前内部阶段建立带版本、阶段和范围修订关联的持久任务；不得在普通内部节点空闲休眠。版本归档后才进入休眠，等待制作人给出下一版本方向，不再从 `docs/status.md` 自动制造正式版本。版本策划、被主策升级的模块策划、候选版本体验、账号额度、鉴权、产品冲突、不可逆决策或大版本发布会暂停并通知；制作人的下一句自然语言会被关联到相应恢复点。

## 正式版本与开发批次

正式版本依次经过方向、版本策划、制作人评审、详细策划、主策审核、任务拆分、版本排期、开发、版本测试、缺陷修复、候选构建、制作人体验和归档。机器状态位于 `.daoyan-agent/releases/`，长期档案位于 [`versions/`](./versions/README.md)。

这 13 个阶段与节点保持同一顺序，每个阶段 ID 只出现一次，但并非每个版本都要执行全部节点。阶段策略可将非固定门禁标记为 `skip`；看板明确显示“无需执行”和公开理由，这些节点既不算完成，也不进入版本进度分母。`reduced` 会把缩减理由和复用依据写入执行 Agent 的任务上下文，不等同于完整执行。纯文档版本会保守裁掉没有运行时价值的详细策划复审、独立排期、运行时 QA 和候选构建；存在真实工作项时不能跳过开发。方向记录、版本策划、制作人立项评审、制作人候选体验和最终归档不可跳过。全队列对账优先将活动指针指向仍占用工作区的运行，并兼容保留当前正在等待回复的决定上下文；无关历史待办不会抢占指针或填入刚释放的活动位置，但仍通过待办保留并阻止派发。PM 已退出而子 Agent 尚存活时继续跟踪；子 Agent 退出后清除占用，后续对账依据恢复点中的 PM 身份保持退出结论。

原 `producer:version` 已改名为内部的 `producer:batch`。开发批次可以顺序交付多个 Feature，但不能自行立项、跳过策划评审、宣布版本通过或触发发布。

任务拆分阶段除人类可读文档外必须提交 `task-breakdown.json`，秘书校验稳定 ID、依赖引用和非空范围后写入正式版本工作项；不再生成笼统占位任务。开发入口按工作项核验当前范围最后一条 Feature 自测，后续失败会使历史通过失效。候选入口对 execute、reduced、skip 修复策略统一校验最新独立 QA：必须是当前范围的可信通过结论并包含回归测试。修复后的失败或阻塞结果会使旧通过结论失效，即使没有未关闭的 blocker/high 缺陷也不能生成候选；跳过修复另需无待修缺陷。存在缺陷时，修复 Agent 只能把缺陷送入待复验，秘书随后创建独立的复验事项；只有第二个测试身份提交当前候选修订的通过证据后才能关闭缺陷。

内部阶段使用带阶段标识的单任务计划，不再把阶段提示重新解释成制作人的新方向，也不会因提示中描述风险而重复请求立项批准。主策要求修改时退回详细策划并自动重排；QA、缺陷复验和候选构建完成后，秘书同时核对报告文件列表与 Git 修订差异，发现 `docs/` 外的未测试变化就拒绝推进。

阶段推进后必须重新读取正式版本状态；一旦进入制作人门禁，其他已排队开发也不得越过门禁启动。版本写入发生修订冲突时，内存变更和事项消费标记不能生效，秘书用最新持久状态重试。任务拆分每轮都重新校验当前清单并替换旧范围，明确标为无需执行的工作项不要求伪造类型检查或测试通过证据。

阶段 PM 的“任务已交付”只证明该阶段工作已执行，不能直接推导策划批准、Feature 完成或 QA 通过。主策审核、开发、QA、缺陷修复和复验分别提交 `design-review.json`、`development.json`、`qa.json`、`bugfix.json` 和 `bugfix-reverification.json`；notice guard 校验角色结论、逐项 ID、命令、证据和候选修订后才写入正式版本。QA 发现缺陷时以 failed 结论完成测试阶段并进入修复，不会把发现问题误记为测试通过。缺少当前阶段 Markdown 或结构化清单时，阶段保持原位并自动安排修复，不使用 charter 或状态文档代替。

## 当前部署范围

候选 QA 同时绑定范围和当前已记录的代码修订。Feature 自测、缺陷重开/开始修复及提交复验会保存 QA 失效边界；历史通过记录保留可审计，但必须在该边界之后取得对应代码修订的独立回归通过结论。即使复用了同一个修订标签、只有 medium 缺陷或使用 reduced 策略，也不能沿用修复前 QA。旧数据缺少边界时仍可读取，已知修复修订与 QA 不符则保守阻止候选。

本机 notice guard、持久队列、任务节点事件、HTTP 收件口、通用 webhook 与钉钉 Stream 通道已经属于仓库能力。钉钉绑定需要在部署机器提供企业内部应用凭据与制作人白名单，凭据不进入仓库。

钉钉首次绑定使用 `npm run secretary:dingtalk:setup` 在本机隐藏输入凭据；制作人无需把 Secret 发给 Codex 或秘书。向导完成后会自动重启守卫并显示连接状态。

原手机版 Sites 仅保留为可恢复的只读快照实验，当前暂停投入和发布维护；它不是秘书入口，也不是项目状态真相。独立移动看板可在通讯闭环稳定后，继续复用现有 HTTP 状态接口建设，不需要改动秘书内核。
