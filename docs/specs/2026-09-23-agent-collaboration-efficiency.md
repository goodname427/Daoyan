# 多 Agent 协作效率与可审计成本

- 状态：实施中
- 负责人：主 Agent（工作流控制面）
- 创建日期：2026-09-23
- 最后更新：2026-09-23

## 问题

正式版本开发阶段存在多次 Agent 调用、重复取证和沙盒 `spawn EPERM`。旧报告只汇总进入最终报告的已知 token，漏记部分失败或恢复调用；候选反馈被误排到下一版，造成重复排期。Feature PM 等待子进程时没有模型调用，不能把长等待时间误算为 token 消耗。

## 目标

- 候选验收退回留在当前版本，形成可执行、可复验的修复项。
- 明确关联的新草案吸收旧候选时，持久记录合并关系并发出排期更正。
- 版本节点展示调用数、已知 token 下界、缺失调用数和参考阈值；未知不按零计。
- 同一 Feature 的直接依赖工作项共享有限长度、带来源的公开结论。

## 非目标

- 不改游戏、产品方向或制作人门禁。
- 不把历史 `spawn EPERM` 环境失败改写成测试通过，不绕过完整门禁。
- 不在质量对照前全局降级模型、合并正式工作项或重写 Feature PM 等待机制。

## 用户流程

制作人否决候选时，秘书记录验收反馈并回到当前版本修复与独立复验；重新交付候选后再请制作人体验。制作人查看中枢的任一版本节点时，可看到该节点可观测的调用和用量。新方向与旧候选明确合并时，旧候选退出待办并留下更正记录。

## 验收标准

- [x] “当前候选不通过，不要……”不会被识别为新版本方向；重放同一消息不重复创建修复项。
- [x] 修复环节有真实待修项，后续仍需独立复验。
- [x] 三条已知重复候选以稳定请求 ID 并入新草案，保留审计与更正通知。
- [x] 节点用量从调用日志读取；没有 footer 的调用单独计数，门禁命令不算 Agent 调用。
- [x] 依赖上下文仅引用已通过的直接前驱，限制长度并附来源路径。
- [ ] 下一轮正式 Feature 对比共享上下文前后的重复检索、总 token、用时和返工率。
- [ ] Luna 在机械任务上的对照实验满足同质量、同门禁、成本降低后再调整路由。

## 技术方案

候选验收退回在 `recordApproval` 中登记为高优先级制作人反馈项，复用现有 bugfix 与独立复验链；这是验收未满足，不等同于版本 QA 产品缺陷。自然语言识别先判断明确候选退回，再判断新产品方向；不能把“新的产品方向，不要视为已发布”当退回。旧候选合并须指定目标版本 ID 和来源请求 ID，执行时要求秘书进程已停止；不使用主题模糊匹配。

用量以每次 Codex 调用日志的 token footer 为依据，节点阈值是预设参考量，不代表硬额度或账单；缺失调用保留未知。历史开发节点的日志可见 18 次调用、约 191 万已知 token，旧报告为约 181 万，说明最终汇总低估了失败/重试路径。秘书语义判断现也记录独立用量事件，但不归属某个版本节点。

Feature PM 等待执行 Agent 是 Node 等待子进程和 20 秒状态心跳，未继续请求模型，故“改成休眠”本身不能节省模型 token。耗时和磁盘心跳可另行优化，优先级低于重复推理。共享上下文只从任务直接依赖的公开输出抽取最多四项、每项 350 字摘要；最终阶段汇总已有前序证据索引，不重复注入。沙盒失败仍按真实退出码登记，完整门禁由可运行宿主独立完成。

模型路由暂保持：Luna 用于轻量检索/文档，Sol 用于常规功能与高风险核心，Astra 用于不可逆架构。下一轮仅对纯机械参考更新或格式化汇总做 Luna/Sol 对照；按接受的任务总 token、总调用、墙钟、审查退回与门禁结果比较，不只看单次模型价格。失败回退成本计入试验。

## 验证计划

- 单元/集成：验收语言、版本反馈幂等、候选合并、用量缺失、依赖上下文、真实秘书 HTTP 收件。
- E2E：中枢节点详情能展示用量字段；完整门禁覆盖浏览器路径。
- 手工体验：秘书保持停止时检查当前历史版本和新草案状态；不启动产品开发。
