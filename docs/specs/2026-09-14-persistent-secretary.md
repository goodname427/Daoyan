# 常驻项目秘书与 notice guard

- 状态：已完成
- 负责人：AI
- 创建日期：2026-09-14
- 最后更新：2026-09-19

## 问题

原来被称为“秘书”的角色实际只是单次 Feature PM：Feature 或版本结束后生命周期终止。制作人必须主动检查运行、重复描述新想法并手工决定何时启动下一轮，失败和完成也缺少异步通知。

## 目标

- 常驻维护跨 feature、跨版本的项目队列与状态。
- 新想法先判断已完成、正在执行、已有排期或尚未安排，再回答或排队。
- 当前交付结束后自动推进队列；版本 Review 节点主动通知并暂停。
- 每个执行任务完成后发送简短、可去重的节点通知，并保留未来可视化需要的结构化明细。
- 通过外部 notice guard 事件唤醒，空闲时模型 token 消耗为 0。
- 为通讯软件提供不绑定供应商的收件和通知边界。

## 非目标

- 不让常驻秘书直接编辑、验证或提交代码。
- 不开放多个 Agent 在同一工作区并行写入。
- 不在仓库保存聊天平台 token、机器人密钥或公网网关配置。
- 不以高频轮询替代事件通知。

## 用户流程

1. 首次运行 `npm run secretary:start`；notice guard 进入事件休眠。
2. 制作人通过 CLI 或通讯网关提交想法；秘书仅在此时唤醒语义判断。
3. 已完成或正在做的方向立即返回项目事实；已排期或全新的方向进入持久队列。
4. notice guard 串行调用 Feature PM。小任务通过时发送简报；Feature PM 完成后再发送整体事件，秘书通知制作人并决定继续队列或休眠。
5. 外部额度阻塞按登记时间恢复，不持续重试；版本完成后保持 Review 暂停，直到制作人给出新方向。
6. 秘书请求产品决策后，制作人以 `--decision` 或通讯消息的 `decision: true` 回复，答复回填原恢复点。

## 验收标准

- [x] notice guard 无固定轮询和常驻模型调用，空闲状态为事件阻塞。
- [x] 收件箱、答复、队列、当前运行和恢复时间可跨进程恢复。
- [x] 项目事实支持 completed、active、scheduled 和 new 的保守查重。
- [x] 新任务复用 `producer`/`producer:version`，不复制交付逻辑。
- [x] 任务完成事件包含标题、Feature/版本父级、完成时间和运行目录，并在 guard 重启后去重。
- [x] 外部额度与鉴权阻塞延时恢复，并具有自动恢复上限。
- [x] 提供本机 HTTP 收件口与通用、飞书、企业微信、Discord 出站 webhook。
- [x] 版本到达 Review 节点后不自动越过制作人。

## 技术方案

- [`../../scripts/secretary-notice-guard.ts`](../../scripts/secretary-notice-guard.ts) 是无模型常驻层，以 `fs.watch`、HTTP、child `close` 和单次 timer 接收事件。
- [`../../scripts/project-secretary.ts`](../../scripts/project-secretary.ts) 提供启动、停止、状态和收件 CLI。
- [`../../scripts/secretary-state.ts`](../../scripts/secretary-state.ts) 保存可单测的状态机、项目事实抽取和本地查重。
- 人类消息默认调用一次 Luna 语义分流；精确项目事实由本地规则直接回答，额度或 CLI 不可用时回退本地规则。
- 采用 [ADR-0012](../adr/0012-事件驱动常驻秘书与交付PM分层.md) 的职责和唤醒边界。
