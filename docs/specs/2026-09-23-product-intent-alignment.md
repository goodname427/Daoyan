# 开发前的产品意图对齐

- 状态：实施中
- 负责人：主 Agent（工作流控制面）
- 日期：2026-09-23

## 问题

制作人常用例子表达尚未整理完的系统想法。旧版本策划门禁只检查价值、范围、非目标和验收是否齐全；主策随后检查这些文字的覆盖与技术自洽。一个把例子误当封闭任务清单的策划也可能连续通过，再被拆成耗时的开发工作。代理评审可以检查一致性，但不能据此推定制作人的隐含意图已得到对齐。

## 范围

- 版本策划先归纳制作人信号、推断的共通原则、至少两个未逐项指定的相邻情形、推荐玩家体验、适用边界及待确认假设。
- 策划与结构化对齐记录一起交付；制作人立项待办先展示核心原则和推荐体验摘要，再链接完整策划。制作人可直接退回修改，无需拆解技术任务。
- 详细策划和主策审核复核相邻情形。只为原例子打补丁时退回策划；出现需要制作人取舍的假设时升级，不自动变为已批准决定。
- 当前已过立项门禁的正式版本保持历史批准事实；新增验证从下一次版本策划交付开始。

## 非目标

- 不要求制作人提交规范化需求或选择工程方案。
- 不为每个局部修复增加独立审批节点。
- 不宣称 JSON 格式检查能够证明主观理解一致；制作人评审仍是最终方向信号。
- 不改动当前游戏版本的产品语义或历史审批记录。

## 制作人流程

制作人自由描述方向和例子 → 主策补全并提出系统原则与推荐体验 → 立项待办先显示短摘要 → 制作人确认或用自然语言指出偏差 → 主策在同一草案修改 → 获批后再做详细设计、任务拆分与开发。若由代理评审，代理须检查推理质量，并把无法凭原话判断的产品假设留给制作人。

## 验收标准

- [x] 版本策划提示要求区分原始信号、策划推断和待确认假设，并验证两个相邻情形。
- [x] 缺少、格式错误或修订不匹配的意图记录会阻止版本策划阶段交付。
- [x] 立项待办展示策划推断的核心原则和推荐体验，制作人可退回到策划阶段。
- [x] 详细策划及主策审核提示要求核对相邻情形与系统原则。
- [ ] 在真实 notice guard 运行中完成一次新版本策划、退回、修订及批准的端到端体验。

## 实现

沿用既有 `charter-draft → charter-review` 门禁，不增加版本阶段。`intent-alignment.json` 绑定版本 ID 与策划修订；策划交付时解析并写入节点摘要，供制作人待办展示。审核提示在后续阶段引用同一记录。格式校验是最小机器门槛，真正的方向判断仍由制作人完成。
