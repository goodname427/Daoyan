# 开发批次持续调度（原版本级调度）

- 状态：已被 ADR-0013 取代；保留为开发批次历史规格
- 负责人：Codex
- 创建日期：2026-09-14
- 最后更新：2026-09-14

## 问题

现有 `producer` 可以把一个 feature 拆成多个专业任务并完成交付，但制作人仍需要每完成一个 feature 就重新发起调度。直接将整个版本的所有工作一次交给单个 Agent，又会混淆上下文、验收边界和失败恢复点。

## 目标

- 制作人只向常驻秘书提供版本方向，版本 Feature PM 从 `docs/status.md` 按优先级选择多个 Feature。
- 每个 feature 保持独立任务合同、模型路由、完整门禁、审查和 Git 交付。
- feature 失败时自动续跑和强制接管，不在首个中间故障就打断制作人。
- 运行可在进程中断后恢复，并在有界队列完成后产生可 Review 报告。

## 非目标

- 不并行让多个 Agent 修改同一工作区。
- 不在一次运行中无限追加新发现的任务。
- 不自动发布大版本，不代替制作人体验验收。
- 不绕过单 feature 的 Definition of Done。

## 交付流程

1. 读取 `docs/status.md` 的“当前首要任务”和“下一阶段候选”，去重后按文档顺序冻结队列。
2. 使用 `agents/policy.json` 的 `versionCycle.maxFeatureRounds` 限制本次范围，其余候选记入延后列表。
3. 为每个 feature 创建稳定的 `.daoyan-agent/runs/` 目录，顺序调用现有 `producer`。
4. 子运行失败时先按恢复点续跑，再按策略强制接管；恢复耗尽才标记版本可恢复中止。
5. 子运行要求制作人决策时立即暂停队列，保留已交付轮次。
6. 所有 feature 交付后重新运行 `verify:full`；通过后标记 `review-ready` 并生成汇总报告。

## 验收标准

- [x] 只读模式可以展示从状态文档冻结的有界 feature 队列。
- [x] 同一 feature 拥有稳定运行目录，版本恢复不重复已交付轮次。
- [x] 失败自动续跑和强制接管次数可由策略配置。
- [x] 版本运行只在全部 feature 交付且最终完整门禁通过后成为 `review-ready`。
- [x] 制作人决策、恢复耗尽和外部阻塞不会被静默跳过。
