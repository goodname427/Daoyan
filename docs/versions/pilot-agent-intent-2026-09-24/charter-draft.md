# 自洽的实体与法术世界：版本策划草案

- 版本 ID：`pilot-agent-intent-2026-09-24`；策划修订：`2`；范围修订：`3`。
- 状态：**制作人评审前的主 Agent 草案**。须经正式主策复核、独立审查和制作人立项评审；本稿没有授权详细策划或开发。
- 目标：纠正上版把“统一规则”落实为实体特例和固定能力入口的偏差，用小范围纵向体验验证可复用的世界规则，不能只补一个法球功能。

## 原话、推断和边界

上版[制作人原始方向](../../../.daoyan-agent/releases/versions/draft-2026-09-23-7af7515c-4ac5-47fe-9063-.json)要求属性驱动、统一实体、资源守恒、事件化法术和“万物皆法术”；修士、法球及未来实体复用能力语义，法球有注入资源、事件与行为法术，不自动回蓝，也不能凭空伤害或无成本持续运动。

制作人本次进一步明确：法球与修士的生成、施法、事件触发和资源消耗应按同一规则解释。法球碰撞造成伤害，是“碰撞事件 → 调用伤害法术”；修士受伤调用法术亦同。法球施法资源由创建者注入，法球自身不能恢复。飞行、爆炸、伤害、元法术价格和算法优化都需要因果与成本解释。更多预设法术应展示特性，敌方修士也要同步。**元法术只表示不可由既有元法术组合表达的原子操作**；读取敌人位置加移动可构成追踪时，追踪应是普通组合术。法球与追踪是检验整体框架的例子，不是封闭的开发清单。

以下是主策待验证的系统推断，并非制作人已批准的设计：

1. **统一实体合同，能力显式声明。** 修士、法球和未来实体共享身份、创建、授权、事件、施法、账本、失效和审计规则；可拥有不同能力和恢复规则。法球无需假装有生命或回蓝，但不能因实体类型不同获得隐藏施法特权。
2. **世界行为由法术组合。** 普通法术编排原子读取与效果形成运动、命中、爆炸等行为。离散事件选择已绑定法术；持续行为的调度、感知与做功需有界付费。惯性和物理模拟不必每帧运行玩家 DSL。
3. **元法术原子且价格可解释。** 组合能实现的追踪、爆炸流程或战术不得因方便而成为新元法术。读取、状态占用、世界效果和执行工作分别定价；更优算法因减少真实工作而省资源，不能无依据打折。静态上界仍不低于实扣。
4. **资源有来源与终点。** 创建者向法球注入有限资源；法球按获准账户付款，耗尽即失败或停止，不借用创建者未来法力。事件、感知、运动、伤害、范围效果、损耗与退款都须可追溯。
5. **事件语义跨实体一致。** 受伤、碰撞、耗尽、消失等事件先提交事实，再按稳定顺序运行绑定法术；上下文、信息权限、重入边界、死亡/消失后的授权和失败语义统一。

代理审核只验证证据和内部一致性，不能代替制作人确认这些隐含意图。

## 相邻情形检验

- 修士受伤与法球碰撞都能绑定普通法术。事件只交付获准事实；响应使用同一 VM、授权、付款和失败合同。
- 敌方修士创建法球，与玩家使用相同的创建、注能、绑定、耗尽和死亡规则；AI 只决定何时选择施法。
- 爆炸、陷阱或护盾也应能从事件和原子效果解释其触发、范围、付款、占用及结束。本版不因此承诺全部实现。
- 多响应争用一笔余额时按稳定顺序原子扣款；创建者死亡后只允许预先声明的有限授权继续，不能免费施法或重复退款。

## 建议的小规模版本闭环

先定义共享执行上下文、实体能力、事件与施法入口、法球账户/恢复限制、原子元法术判定、成本账本和旧语义迁移；核对 ADR 0017–0020 与架构不变量。难以撤销的选择先写 ADR。范围限于一条贯通路径，但必须走共享规则，不能在旧特例上加一个碰撞回调。

推荐路径是：修士以普通法术创建并注能法球，为它绑定碰撞响应和组合运动程序；法球以自身授权执行，碰撞调用可复用伤害法术，余额不足时可观察地失败。把“读取位置 + 施加运动”构成的追踪作为可编辑普通预设，并决定旧 `设置法球追踪` 的迁移。增加少量**机制不同**的预设，至少展示事件响应、感知与运动组合、资源耗尽/失败；敌方修士至少有一条同管线的法球或事件施法行为。具体预设数量由详细策划按闭环确定，不用换皮数量替代机制展示。爆炸先作为设计检验案例；若所需原子效果已具备且范围允许，可做成预设，否则列入下一期并说明缺口。

玩家应在推演台读懂、导入和修改这些法术并检查预算，在演武场看见玩家与敌方修士按同一规则施法、触发、扣款、耗尽，再返回同一法术书修改验证。每次效果都能回答：哪个事件启动、谁执行、用什么原子效果、哪笔资源付款、何时结束。

验收需覆盖修士与法球的同构事件合同、无资源/无权限、重复接触、并发争用、消失/死亡、静态上界与实扣，以及旧法术/存档等价迁移或明确拒绝。真实体验覆盖推演台、预设导入、演武场玩家/敌人、账本和往返。独立审查寻找仍藏在实体类型分支里的免费行为或可组合元法术。若共享底座超出小版本容量，Version PM 应提出逐期可玩的闭环，并保留全部方向，不暗中缩回单点补丁。

非目标：一次实现所有未来实体及玩法；让惯性或 UI 每帧运行 DSL；把协作流程改造写成游戏主题。

## 需要制作人确认

1. “同一套规则”按**统一执行与计费合同、能力差异显式声明**理解，是否符合预期？
2. 先做“创建注能 → 组合运动 → 碰撞事件 → 法术伤害”的共享闭环，同期补预设和敌方修士，爆炸先作设计案例，这个优先顺序是否对？
3. 旧复合元法术可能需兼容迁移或定位拒绝。是否有必须原样保留的旧体验？
