# 首批 A 策划体验验收任务

范围修订 **13**，节点 **design-acceptance**。问题是独立判断已交付行为是否兑现批准策划；本次只规划，不执行体验、开发或后续节点。依据为 [drb9 批准结论](./design-review.md)、[模块方案](./module-design.md)、[开发合同](./development-tasks.json)与 [ADR-0023](../../adr/0023-策划黑盒体验验收.md)。

只设一个成果任务 **`da-a-flow`**：未参与两项开发实现的主策或策划，对三行为及同书玩家闭环作一次完整黑盒验收。各场景涉及共同来源、程序身份、付款和失败余态，分给多个 Feature PM 会重复操作与判断。任务内部操作顺序由 Feature PM 安排，不另拆调研、执行、测试或报告任务。同节点无前驱，`dependsOn=[]`；开发接纳与可核查运行来源是阶段前提，不写成不存在的同节点任务依赖。

生命周期记录已将 development 标为 completed、design-acceptance 标为 active，来源为正式 development-11；[开发正文](./development.md)及 [development.json](./development.json)仍记最终集成完整门禁未运行。先核对正式恢复证据、真实退出码及最终树/配置的关联，保留矛盾，不能只凭阶段标志推定通过。缺有效证据时由 Version PM 处理阶段前提，体验任务不补跑完整门禁。历史实玩 blocked 与后续一次性补证分别保留，优先核对最新接纳来源，不复活已关闭的旧缺口。

同树、同配置、同范围的前序命令、无头测量、门禁与实玩素材复用为技术依据和操作线索；本节点新增的是独立策划亲自操作后的玩法一致性判断。一次性主 Agent 补证、DOM 回放和自动化不能代签本节点，不重复运行自动化场景或完整门禁。预算、逐端收据等无法在 UI 直接核验的技术项引用前序来源并明示可见性；批准的玩家必验项不可达则记录偏差或阻断。

采用 **fresh**，原因是开发执行与独立策划验收的角色发生改变，而非固定轮数换会话。之后同作用域、角色、批准范围、模型与推理配置一致且会话可恢复时可续接；独立审查保留与执行分离的只读会话，只核本轮差异及证据，不重复操作。

独占写入仅为本版本 `tasks/design-acceptance-da-a-flow.json` 和 `tasks/design-acceptance-da-a-flow/`。机器合同见 [design-acceptance-tasks.json](./design-acceptance-tasks.json)。共享节点总报告、`docs/status.md`、开发日志与路线图交接由 Version PM 收束，本任务不写。禁止修改产品实现、游戏测试、批准策划或运行状态。

非目标为全量活动战斗迁移、持续驱动/攻击、复苏、法球再次付费响应、更多预设、敌方修士新行为、硬件接入实测及 QA/候选排期。有限来源选择不证明真实硬件/AI 接入。未批准的新解释和不可逆取舍先升级；已批准合同的实现偏差退对应开发成果，保留仍匹配的证据，仅复验受影响场景。任务交付偏差或阻断报告不等于节点通过。
